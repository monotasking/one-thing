## 2. 架构调查、方案与复审

围绕你提出的“减少跨模块改动，让新增能力更容易”，检查了后端装配、会话写入、任务执行、存储、授权、事件交付和宿主退出之间的关系，并制定了 B0–B7 工作包：

1. 建立可信的回归与架构检查基线。
2. 补齐可靠保存与外部动作前的检查点。
3. 统一同一数据目录的独占写入和退出清理。
4. 收拢会话命令、读取、写入与恢复的职责。
5. 固定可信身份，检查实际访问资源的权限。
6. 建立版本化快照、增量交付与断线恢复。
7. 收紧公开接口和依赖边界，验证新增能力的改动范围。

复审时补入了两个重要约束：会话授权不等于整台机器的多用户隔离；旧版本能读账本也不等于可以安全降级写入。后者进一步落实为数据目录最低可写能力检查及完整备份恢复流程。

这次沿用并整理既有 Backend、Feature 和 SessionLayer，没有把应用改成分布式微服务。

## 4. SDK 与发布准备做到了哪里

实现了可选的 SDK 请求检查点适配、请求与结果确认通道、原生文件描述符适配、preload runtime、连接器生命周期和三端物理构建产物。启动前会按实际 command/env/cwd 校验运行时，等待握手；取消或校验失败时不能迟到启动 query。

协商支持的 ACP 路径接入 durableSeq 持久化确认，异常退出后不盲目重放结果未知的动作；这不代表所有第三方 ACP 执行器都已支持或验证该契约。

已经运行过真实 SDK、原生进程和真实 Backend 组合验证，但部分网络传输使用本地合成实现。**默认生产工厂尚未启用完整适配，不能声称所有 SDK/ACP 模型和工具动作都已获得逐次可靠保存保证。**

发布准备中还验证了历史官方 v1.1.7 的隔离启动行为：新旧锁的相互排斥成立，但旧版遇到未知能力声明仍继续初始化并产生业务文件。因此没有把它列为安全降级目标；支持的回滚版本、Windows 和正式发布流水线的验收仍未关闭。曾构建并验证隔离的 macOS 应用包，但没有据此发布或替换用户安装的正式应用。

同时补齐记录源码摘要、平台和实际退出码的隔离验收入口，把标签构建和发布接到同标签源码的测试及架构门禁。配置这些检查不等于已经完成正式发布验证。

## 5. 启动失败与数据锁处理

你反馈的 `Not connected to core`，当时直接原因是数据目录残留了 PID 70476 的旧格式锁。新锁协议不会仅凭 PID 不存在就自动删除旧锁，因此 Backend 无法取得写入所有权。

当时执行了：

- 检查并记录旧锁完整身份，确认相关宿主及启动器退出。
- 使用现有离线恢复接口原子归档原锁，保留原件；没有删除业务数据或放宽锁协议。
- 重建并启动桌面，验证存活进程、锁和 HTTP 发现记录一致，接口及原有会话加载正常。
- 修复重复退出信号过早强制结束 Electron、开发启动器清理时间不足和失败误报等问题。
- 增加默认只读的 `store lock inspect` 和显式离线 `recover` CLI 入口。

这次启动恢复是历史阶段结果。最近一次调查时，新的 discovery/锁指向 PID 76094，该进程已经退出；最新回合有 `run/end: completed`，不能沿用此前重启中止的结论。本轮调查没有处理这把新残留锁，也没有再次启动用户实例或向真实会话自动发送模型请求。

## 6. 流式顺序与卡顿处理

### 6.1 第一轮：减少全量复制和同步积压

服务端不再每个 revision 都重新深拷贝完整会话；客户端按变化路径复制，复用未变化的历史对象。数组新增、截短使用增量补丁，减少新消息携带整段历史进入回放队列。慢消费者的状态合并保留业务事件、ready 和 invalidate 等顺序边界；同一轮重复通知合并捕获。

这一轮处理了真实的同步缺陷，但测试使用合成状态，没有覆盖实际历史消息读取链。恢复后的空闲低 CPU 和接口可用，也没有证明流式滚动恢复。

### 6.2 第二轮：历史缓存与工具前后正文顺序

发现实际同步捕获绕过历史节点缓存，每次重新物化历史，并再次读取 blob、校验哈希。已在 `events-reads` 中按实例、会话、视图和节点版本缓存结果，只重新处理变化节点；历史与 live-ui 缓存隔离，失败读取不缓存，清理时释放相应缓存。

你指出的“工具调用完成后，新正文增加到工具之前”来自实时内容位置契约缺口。为同步专用 live-ui 视图补齐片段坐标和未结束的可见片段；前端按坐标合并，并按动画帧批量发布，保持“正文 A → 工具 → 正文 B”。成功结束先于最终快照时保留已显示内容，直到最终快照接管；旧请求迟到失败不会覆盖新状态。

相关测试和短多工具桌面验证通过，但没有完成真实长会话持续滚动的验收。错误与中止的收尾仍沿用原有时机，不把成功结束的修复扩大为所有终止路径已重新验证。

### 6.3 第三轮：只读调查持续卡顿

收到“仍然很卡，流式中几乎无法滚动”后，停止依据代码猜测修改生产逻辑，新增隔离诊断脚本，采集真实 Electron 主进程和渲染进程的 CPU profile、Chromium 时间线、网络与滚动数据。

生产构建夹具包含 116 轮、232 条历史消息，初次同步约 19.7 MB；新增约 2.9 KB 正文，以每字符约 19 ms 输出。已经得到以下证据：

| 发现 | 能确定什么 | 不能据此确定什么 |
| --- | --- | --- |
| 同步仍遍历历史 | 物化缓存对象与首次深拷贝快照不是同一引用，每次 diff 仍逐字段比较；约 22.9 秒采样中相关 self time 合计约 3.08 秒 | 不能单独解释用户界面全程卡住，也不是每次重新 JSON 克隆全部历史 |
| 一次约 0.95 秒 Layout | 新字“滚”触发字体分片请求，字体加载后约 30 万个布局对象重排，时间线高度吻合 | 未做字体预热对照，不能将字体认定为全部持续卡顿的最终原因 |
| 滚动实际发生 | 81 次滚轮输入全部对应位移；输入至 scroll 回调 p95 约 51 ms，最大约 997 ms | 场景在测量前已离开贴底，不覆盖自动跟随中首次向上翻；回调时延也不等于实际显示时延 |
| 没有重连循环 | 测量期间没有新 SSE 连接或重复全量快照 | 不能保证真实用户现场不存在其他积压或重连问题 |

诊断探针曾用 wheel 处理器执行时的位置作为“滚动前位置”，漏计了合成器已经完成的滚动。已用完整时间线纠正，不再使用“只有 3 次滚动生效”的错误汇总。也修正了把 provider 完成时间与 DOM 检出时间混用的指标。

开发模式补测的三个隔离实例在 Backend 装配阶段启动超时，没有进入性能测量；保留了失败证据，没有将其计入通过结果。最终确认测试进程及临时开发服务无残留。**第三轮只修改诊断脚本和文档，没有提交未经验证的生产性能修复。**

## 8. 尚未完成的工作

按当前优先级：

1. **流式滚动卡顿。** 修复剩余的历史深比较开销；完成自动贴底转主动滚动、开发模式及贴近真实历史结构的复现，验证修改前后的效果。
2. **长会话布局。** 对字体预热与历史布局隔离做对照，确认是否需要限制离屏历史的布局规模，并验证定位、选择、工具展开及滚动位置不回退。
3. **启动等待。** 查清最近隔离诊断实例停在 Backend 装配中的具体等待源；与用户数据目录旧锁故障分开处理。
4. **SDK 默认接线和外部执行器。** 完成真实默认路由、工具动作、取消与恢复的完整验证后再启用。
5. **平台与发布。** 完成 Windows、正式 runner、受支持历史版本及安全回滚路线；最新全部改动还需要联合回归。

本次说明文档没有继续修改业务代码，也没有进行提交、推送、发布或自动运行用户的模型请求。
