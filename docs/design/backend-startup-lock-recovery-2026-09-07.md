# 桌面启动失败：旧锁恢复与退出修复

2026-09-07。状态：应用已恢复启动，核心接口与桌面界面均已验证；退出修复的 15 项组合测试通过。

## 故障原因

`Not connected to core` 是核心启动失败后的界面提示。实际阻塞来自用户数据目录 `/Users/yitiansong/.onething/run/backend.lock`：它是 1.1.7 在 2026-09-03 09:39:18（北京时间）创建的旧格式文件锁，记录 `owner=desktop`、`pid=70476`。现场检查确认该进程已经退出。

本轮架构调整后的锁协议要求显式离线恢复，启动时不会仅凭 PID 消失就自动移除旧锁。因此新启动的桌面进程无法取得数据目录所有权，核心没有完成装配。旧发现记录中的 PID 13338 也已退出。旧锁本身不能证明用户数据损坏；本次没有找到足够的退出日志，无法断言 70476 当时为何留下锁。

## 已执行的恢复

1. 使用现有只读 `inspectStoreLock` 检查锁格式、持有者与完整文件身份，并保存诊断到 `/tmp/onething-startup-lock-reviewed-20260907-1788745664468.json`（权限 0600）。
2. 核对当前桌面与启动器身份，向卡住的桌面进程 26320 发送一次 SIGTERM，等待它、启动器 26315 和 npm 26293 全部实际退出。确认没有自动重启启动器或其他该目录的应用宿主在运行。
3. 使用现有 `quarantineStoreLockForRecovery`，在再次核对原锁身份和持有者已退出后原子重命名归档。未删除业务数据，也未放宽锁协议。
4. 重建桌面入口，按原来的 `npm run app:dev` 方式启动应用。

## 防止再次发生的修复

代码检查发现，开发模式的一次退出信号可能经进程组和启动器重复传到 Electron，而原来的第二次信号会立即 `app.exit(1)`；启动器原来 1.2 秒、2.4 秒的停止阶梯也短于 Backend 默认 5 秒的清理期限。这是已确认的复发风险，但尚不能据此认定为旧进程 70476 的退出原因。

修复把窗口退出、SIGINT 与 SIGTERM 合并到同一份关机 Promise，等待 Backend 的实际清理结果。启动器给子进程 10 秒正常清理时间，接管旧启动器时给 15 秒；以真实 `close` 为完成依据，超时强制停止报告失败并保留锁现场。复核发现的两项关联问题也已修正：清理期间被信号终止不能报成功；超时日志回调抛错不能跳过后续停止和实际排空。

最终组合为 2 个文件、15 项通过，6.27 秒，实际退出码 0，日志 `/tmp/desktop-dev-shutdown-combined-v1.log`。桌面退出的 4 项包括真实子进程、真实 BackendResources/StoreLock、重复信号、超过原 1.2 秒阶梯的保存屏障、成功释放锁，以及受控保存失败时保锁和非零退出。启动器 11 项包括重复信号、真实 exit/close 时间差、固定 PID 快照、超时、清理期间外部 SIGKILL、信号发送错误，以及两个超时观察回调抛错后仍等待真实清理。

桌面完整类型检查通过（`/tmp/desktop-shutdown-types-v2.log`），新增和调整的 5 个 MJS 文件语法检查通过。本次真实信号测试运行于 macOS；依赖 POSIX 信号处理的用例在 Windows 跳过，不把该结果外推为 Windows 优雅退出保证，也未重跑此前整个跨平台全量套件。测试不代表真实磁盘故障或全部 Electron 窗口生命周期均已验证。
