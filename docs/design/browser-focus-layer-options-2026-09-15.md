# 浏览器焦点与层级：解决方案和取舍

## 我的建议

**先修焦点同步；对浏览器 ⋯ 这种标准动作菜单，优先采用原生菜单。** 这能以较小范围解决目前已经复现的两个问题。如果产品要求菜单、Tooltip、Dock、搜索面板都能自由覆盖实时网页，再建设统一的原生弹层承载能力。

如果你更看重菜单与现有界面的外观完全一致，可以保留 React 菜单、改进截图交接，但需要接受弹出等待和网页暂时不能交互的局限。

“网页上方局部不能点击”尚未复现，仍需定位。下面的方案不能直接保证它一起消失。

## 一、焦点修复是所有方案的共同前提

现在的问题可以理解为：你点击地址栏，程序还在处理上一轮“把焦点交给网页”的消息，于是又把焦点送回网页。

### 应该怎样改

1. **分清“通知”和“命令”。** 网页通知“我获得了焦点”，外壳只更新焦点归属；需要同步占位元素时，必须防止它再次发出网页聚焦命令。
2. **以最新用户操作为准。** 用户点击地址栏、菜单后，旧的网页聚焦请求和返回通知不能覆盖它。焦点请求携带递增编号，外壳和主进程共同判定是否过期；单靠收到消息时检查一个 DOM 元素不够。
3. **区分窗口恢复与主动进入网页。** 从别的应用返回时，恢复到原先的占位元素，不等于用户要求重新聚焦网页。主动点击网页、快捷键进入网页仍要正常工作。
4. **弹层打开期间明确焦点归属。** 菜单拥有焦点时拒绝无关网页请求；关闭后只在用户没有转移到其他控件的情况下归还焦点。

| 做法 | 优点 | 缺点 | 判断 |
| --- | --- | --- | --- |
| 在地址栏上补一次 focus，或延迟几十毫秒再 focus | 改动很少 | 只是与网页争最后一次执行；机器负载一变仍可能失效，也会干扰菜单和键盘操作 | 不建议 |
| 把焦点通知、主动转移、过期请求分开管理 | 从产生抢焦点的地方修复；地址栏、菜单、切换应用都受益；外观不变 | 要修改跨进程焦点协议，并验证 Tab、快捷键、关闭弹层等路径 | 推荐，必须先做 |

代价是一次有边界的焦点逻辑调整，不需要替换浏览器内核。现有 67 项测试虽然通过，但缺少真实 Electron 中“点击地址栏时旧消息返回”的场景，必须补上这类验证。

## 二、菜单与网页层级有三种方案

网页是原生视图，React 菜单画在外壳里。提高菜单的 CSS z-index 不能改变它相对原生网页视图的顺序。

| 方案 | 用户体验 | 优点 | 缺点 | 相对改动 |
| --- | --- | --- | --- | --- |
| A. 保留 React 菜单，协调截图交接 | 保持现有外观；打开时等待截图准备；交接期间网页呈现截图 | 复用现有组件；改动集中；可供多种现有弹层使用 | 截图耗时仍在；网页暂时不能交互；动态内容不是实时的；很难保证跨进程绝对无闪帧 | 中 |
| B. ⋯ 改为原生菜单 | 点击后由系统菜单显示；网页继续保持原生显示 | 这条路径无需截图或隐藏网页；键盘与菜单交互可使用系统机制；适合标准动作列表 | 外观随系统变化；无法自由放任意 React 布局；只解决菜单，不能顺便解决 Dock、Tooltip 等 | 小至中 |
| C. 自定义弹层放进独立原生视图或子窗口 | 自定义菜单可覆盖实时网页；有机会统一复杂浮层体验 | 保留自定义外观；减少依赖网页截图；可以覆盖更广的产品需求 | 跨视图状态、布局、焦点、鼠标命中、缩放和生命周期都需要协调；额外资源开销；实施与维护最复杂 | 大 |

这里的大小是根据当前架构作出的相对判断，不是已经验证过的工期估算。

### A：保留截图，改好交接

把当前“菜单先出来 → 等截图 → 隐藏网页 → 再等图片显示”改为有明确准备状态的过程：

1. 请求打开菜单时立即接管焦点，并在后台准备截图和菜单布局。
2. 截图传到外壳并完成解码后，外壳报告准备完成。
3. 协调原生网页隐藏和菜单、截图显示，缩小切换空档。
4. 关闭时丢弃旧截图请求，协调网页恢复与截图撤除；失败时退出过渡，不能永久停在不能点击的截图上。

**优点：** 保留现有 UI，适合当前希望少动架构的阶段。

**代价：** 把“先被遮住”改为“准备好再出现”，没有消除截图的耗时。即使增加回执，DOM 与原生视图的实际绘制也不是天然的一次原子提交，效果需要逐帧验证。对菜单可能可以接受，对频繁出现的 Tooltip、Dock 或需要与网页同时交互的浮窗，局限更明显。

可以先减少不必要的截图，例如按实际遮挡范围处理，但这需要独立的遮挡管理，不能继续用“存在任意菜单，就隐藏全部网页”的粗粒度判断。

### B：浏览器 ⋯ 使用原生菜单

保留当前动作定义，点击 ⋯ 时由主进程将同一份动作映射成原生菜单；选中后仍回到现有业务命令，不复制两套功能逻辑。

Electron 提供 `Menu.popup()`，支持指定窗口、位置和关闭回调；macOS 上使用系统原生菜单。[官方 Menu 文档](https://www.electronjs.org/docs/latest/api/menu#menupopupoptions)

**优点：** 省掉这张菜单的截图交接，直接消除该路径的截图等待和替换闪烁。当前菜单以动作为主，匹配度较高。

**代价：** 字体、间距、阴影等由系统决定，和应用其他菜单可能不完全一致；未来若要在菜单里加入搜索框、卡片或复杂交互，就不适合。原生菜单的开关仍要接入焦点管理，不能认为换菜单就自动修好了地址栏。

这是我对当前 ⋯ 菜单的优先选择，前提是能接受系统菜单外观。

### C：建立真正位于网页上方的自定义弹层

让自定义弹层也成为原生视图树的一员，再明确它位于网页之上。可以先用一张菜单验证独立 `WebContentsView`；需要越过父窗口边界的弹出内容，再评估子窗口，而不是一开始重写全部界面。

Electron 的 `View.addChildView()` 支持调整子视图顺序；`BaseWindow` 支持组合多个网页视图。这些 API 提供构建基础，具体弹层方案仍需原型验证。[View 文档](https://www.electronjs.org/docs/latest/api/view#viewaddchildviewview-index)、[BaseWindow 文档](https://www.electronjs.org/docs/latest/api/base-window)

**优点：** 网页可以继续实时绘制，自定义弹层有自己的原生层级，适合作为长期的统一能力。

**代价：** 原来同一个 React 页面里的组件可能分到不同网页环境中，主题、数据、事件和焦点要建立桥接。尤其要处理鼠标命中：透明只表示看不见，并不代表鼠标可以穿过去。不能简单铺一张全窗口透明视图，否则可能真正制造“上方有一层东西挡住”的问题。应限制弹层实际占用范围，并明确何时捕获、何时放行点击。

## 三、我会按这个顺序落地

1. **先修焦点回送。** 验证地址栏单击后持续获得焦点、从其他应用返回后也正常、旧通知无法抢回焦点。
2. **将浏览器 ⋯ 切为原生菜单，若必须保留当前外观则选 A。** 验证打开、关闭、键盘选择、点击外部、多个浏览器同时打开的情况。
3. **继续定位顶部不可点击区域。** 记录实际点击落在哪个网页/外壳、原生矩形是否偏移、是否残留截图或弹层；根据证据决定是否属于前两项。
4. **只有在多个自定义浮层都必须覆盖实时网页时，再做 C。** 先验证一张菜单，测试窗口拖动、缩放、全屏、多显示器和网页交互，再推广到其他浮层。

目前不建议为了这些问题直接换成 `<webview>`：迁移成本大，也不保证顺便解决焦点问题；Electron 官方当前不推荐依赖这个标签。[官方说明](https://www.electronjs.org/docs/latest/api/webview-tag)
