## 测量范围与环境

环境：Apple M3 Pro，12 个逻辑 CPU，18 GiB 内存；macOS/Darwin 25.5.0 arm64；Node v22.22.3；临时文件系统 statfs type=26。修复前测量开始于 13:52:47 UTC，修复后开始于 14:03:10 UTC。第一轮开始/结束的 1 分钟系统负载为 6.76/7.67，不能把这台并行开发机器当作无干扰专用性能主机。

- 会话历史分为 10、100、1000 回合。每个历史回合使用生产 `SessionEventLayer` 写入用户消息、run、request、256 个正文 delta、工具调用及结果；生产编码器保持 64 条/2 秒批量设置。历史构造不计入检查点耗时，并且每 20 回合排空构造队列。
- 创建生产活投影后预热一回合，再记录 20 回合 × 5 个语义检查点。每回合 256 个 64 字节正文 delta；测量回合的工具结果引入一个新 32 KiB blob。计时从调用 `flushSessionEventLog` 开始，包含等待真实 append、blob 校验及同步、日志 fsync、必要目录屏障；不包含模型、工具本身或预先生成 blob 的时间。
- 每档有 10 个独立 Node 子进程做冷恢复，输入是复制到独立目录的持久化未结束 run/工具记录。计时包含生产 prepare、恢复事件耐久化、投影重建和消息物化，不包含构建、进程启动及复制时间。每次断言只修复一个 run/工具、完整消息数量正确、结尾为 interrupted，第二次 prepare 不增加文件字节。
- “冷”指进程缓存为空；没有逐出操作系统页缓存，也没有模拟断电。这是会话事件能力测量，不是整个 Backend 启动或 UI 首屏耗时。
- p50/p95 使用 nearest-rank；20 次样本的 p95 是第 19 个值，10 次和 5 次样本的 p95 等于最大值。RSS 仅为相应进程采样时的总量，不作业务净内存或精确分配峰值。

| 调工具前 | 4.98 / 15.33 | 4.87 / 5.26 | 4.73 / 5.25 |
| 工具结果含新 blob | 7.43 / 53.02 | 6.13 / 6.98 | 59.13 / 67.53 |
| run 结束 | 4.56 / 11.07 | 4.80 / 5.38 | 4.68 / 5.39 |

| 冷恢复阶段 | 10 回合历史 | 100 回合历史 | 1000 回合历史 |

测量回合结束时 journal 约为 0.58 / 2.25 / 18.99 MiB。追加未结束回合并恢复后分别为 347 / 1337 / 11237 条事件，64 / 244 / 2044 条消息。prepare 的倒扫窗口虽是 4 MiB，首次恢复写入还会初始化真实 writer/surface，不能把这一列解读成仅有尾扫 IO。

两个完整运行都显示普通检查点没有随 10 倍历史体积产生相应的热路径增长；生产缓存已建立后，检查点主要等待新增写入及同步。blob/恢复的同步耗时存在明显运行间差异：修复前 1000 回合档新 blob 检查点 p50/p95 为 5.13/5.32 ms，修复后为 59.13/67.53 ms；反过来小档第一轮更慢。没有证据把这种非单调差异归为代码退化，因此保留原始数据，没有通过扩大批量、减少 blob 校验或跳过 fsync 来制造更好的数字。

正常测量回合中的三个历史档均观察到：journal 在途操作峰值 6（包含检查点），未检查点事件峰值 5，encoder 正文负载峰值 4096 字节。20 次回合期间未主动再次读取投影，事件尾巴记录峰值为 231。这些是该负载下的实际峰值，不是任意并发和任意慢盘下的硬上限。

## 流缓冲测量与修复

共用 `SessionStreamCoalescer` 仍使用真实 16ms 定时器。输入为 64 字节 delta，正文/推理交错；每档 500ms、5 次。第一轮在 100 / 1000 / 10000 条每秒下，尚未交付的纯正文负载峰值 p95 分别为 128 / 1216 / 12736 字节，完整输出字节数与输入相等。这不包含 JSON 信封、对象分配、网络缓冲或内核 TCP 队列，也不证明事件循环长时间阻塞时合批器有固定容量。

真实 HTTP 项使用生产 HTTP 路由、合批器、Node response 和回环 TCP；只有事件源是受控负载。每次尝试输出 8 MiB，单条 delta 8 KiB，每 8 条以业务事件触发保序 flush。对照组正常读，慢组先暂停读取，在生产者完成后再停 100ms 才恢复读取；每组 5 个独立进程。

| Node `response.writableLength` 峰值 | 正常读者 p50 / p95 | 暂停读者 p50 / p95 |
| --- | ---: | ---: |
| 修复前 | 65,986 / 65,986 B | 7,109,033 / 7,635,617 B |
| 修复后 | 65,701 / 65,701 B | 65,701 / 65,812 B |

修复前 `writeSse` 在 `write(false)` 后继续写入，慢读者积压接近整个 8 MiB 负载。新增 [sse-delivery.ts](../../packages/backend/server/sse-delivery.ts)，目前接入主 `/api/events` 通道：

> 2026-09-07 撤回：会话同步协议已整条删除（第二套真相），见 docs/audit/session-sync-retirement-2026-09-07.md

1. 单连接已编码待发队列硬上限 1 MiB，按 UTF-8 字节计算，含保留给恢复控制帧的 1 KiB。每次向 Node 写不超过 64 KiB，收到 `false` 后等 `drain` 再继续；Node 自身缓冲的上界还包含其 high-water mark，不能把单次写块大小当成整个 response 的硬上限。
2. 超限时停止接收后续事件，完成已经开始的 SSE 帧，丢弃尚未开始的帧，并显式发出恢复指令后结束连接。没有静默把未交付状态当作成功；30 秒没有 drain 则销毁连接并释放队列、订阅和监听器。
3. `sync=1` 使用现有 `session:sync invalidate(buffer-overflow)`，客户端清掉 revision 后重新请求独立的 `/api/sync` HTTP 快照。单个超大 commit 也走这条路径；完整大快照不塞回受限 SSE 队列，避免重复重连到同一个大 patch。
4. 旧 `sync=0` 通道收到 `transport:resync-required` 后断开。它本来没有完整的状态恢复契约，不能声称旧消费者会自动补齐瞬时 delta。

修复后正常读者 5/5 收到完整 8 MiB。暂停读者 5/5 收到明确恢复指令并断开，实际收到的部分负载记录在 JSON 中；这不是“慢客户端仍完整交付 8 MiB”的宣称。另一个真实 HTTP/现有客户端测试发送 9 MiB UTF-8 的会话状态提交，证明只重连一次、完整快照内容一致、后续普通更新继续到达。

1 MiB 限制的是交付层保留的编码队列。领域当前快照、生成 JSON 时的临时字符串、内核 socket 缓冲不包括在内。其他独立 SSE 路由（如 scratchpad/文件监控的初始快照）暂未接入这次主事件通道的恢复协议，不能把本结果扩张为所有 SSE 路由已经有界。

## 验证与后续比较条件

已执行完整基准两轮、小样本探针和最终 HTTP 单独复测。SSE 有界交付/Unicode/未完成帧/停滞释放、真实 HTTP 大提交恢复、实际 Backend 同步客户端、设置 SSE、HTTP 路由与客户端解析等最终相关回归为 8 个文件、76 个测试通过。新增实现和探针通过类型检查；boundary 为 0，assembly 无新增模块级状态，transport 四壳合计由 1004 降为 1001 行，无指标上升；未修改任何门禁基线。

后续比较应使用相同 Node、机器、文件系统、负载配置与完整原始样本，分别比较 checkpoint、耐久恢复、物化和发送缓冲。若普通 checkpoint 随历史增长，先检查缓存或额外全量扫描；若仅 blob 同步变慢，先排除文件系统/系统负载并复测。性能门不能以跳过可靠性屏障为通过条件。本机数据不代替 Windows/Linux、真实模型端到端延迟、整宿主冷启动或任意大历史的容量验收。
