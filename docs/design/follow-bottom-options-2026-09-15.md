# useFollowBottom：设计评价与替代方案

## 我的判断

**基础路线合理，当前实现的职责已经过于集中。我会保留原生滚动和尺寸观察，把“谁决定这一帧的位置”重新整理清楚。**

不能因为这次微抖就认定整个设计错误，也不能因为已有很多测试，就认为继续加局部补偿足够稳妥。这次录屏证明了微抖存在，但没有证明究竟是哪一个分支造成。

## 当前方案好在哪里

当前实现可概括为：判断是否跟随 → 观察内容高度 → 跟随时滚到底部 → 再补偿尾部位置。

- **跟着实际布局走。** 换行、图片加载、工具卡展开都可能改变高度；观察尺寸比只监听新 token 更贴近真正的滚动需求。
- **保留原生浏览体验。** 滚轮、触控板、文本选择、查找和普通文档布局仍沿用浏览器能力。
- **已有明确的跟随/浏览区分。** `follow.ts` 中的状态机和未读提示逻辑值得保留；用户翻看历史时，不应被新输出拉回底部。
- **覆盖了真实产品场景。** 发送留白、会话切换、历史内容恢复、折叠和重试都已有处理，重写时需要承担这些行为的回归成本。

## 当前设计的主要负担

### 一、一个 hook 同时管理了多种定位需求

它不只是“跟到底部”，还在管理发送后定位、底部留白、折叠期间保持阅读位置、恢复历史位置、重试动画，以及像素补偿。

这些需求各自有道理，但需要明确回答：**这一刻究竟应该听谁的？** 当前答案分散在状态、引用变量、时间窗口和观察器分支里。问题不在文件行数，而在修改一个行为时，需要推演其他行为会不会同时介入。

### 二、布局位置与视觉位置是两套数

`scrollTop` 改变滚动位置，`translate` 又改变整条回复的显示位置。后续测量若读取已经补偿过的几何，就必须始终区分自然位置、补偿值和最终位置。

这种方案可以做正确，但验证成本高。当前“只能向上补偿”没有被函数完整保证，就是一处已经证实的边界缺陷；它是否造成此次微抖，仍需对照。

### 三、浏览器也可能调整位置

当前保留了浏览器滚动锚定。它有助于防止阅读位置因上方布局变化而跳动，但应用自身也在保存和调整锚点。两者需要明确分工，不能假定浏览器每次都会做同样的补偿：规范列出了尺寸、边距、变换等变化可以抑制锚定的情况。[滚动锚定规范](https://www.w3.org/TR/css-scroll-anchoring/#suppression-triggers)

### 四、测试还没有充分覆盖“正文是否稳定”

目前部分测试检查底部提示的位置，部分检查字数不减少。它们都不足以单独保证正文中同一个段落没有反向微移。换任何实现，都需要保留这次录屏暴露出的验收标准。

## 有哪些方案，各有什么取舍

以下是针对本项目的设计判断，不是已经跑过对照后的性能结论。

| 方案 | 怎么做 | 优点 | 缺点与风险 | 对本项目的判断 |
| --- | --- | --- | --- | --- |
| **A. 保留当前实现，做局部修复** | 修补已定位的时序或补偿问题，补回归测试 | 改动小；现有交互保持；适合尽快修复明确根因 | 多种定位需求仍交织，后续改动的推演成本不会明显降低 | 适合作为近期修复，前提是先复现并证实原因 |
| **B. 原生滚动 + 集中决策** | 仍用尺寸观察，但由一个控制器决定保持阅读锚点、贴底或执行明确跳转，再统一提交位置 | 定位规则可解释；冲突更容易测试；保留原生滚动能力 | 重构成本中等；需要迁移留白、折叠、恢复等行为；仍需处理像素精度 | **最推荐的长期方向**，属于整理现有路线，不是全部推倒 |
| **C. 主要依赖浏览器锚定/CSS** | 用底部标记辅助锚定，减少应用主动滚动 | JS 少；简单消息列表容易实现 | 浏览器锚定旨在保持可见内容位置，并不自动等于持续贴底；发送定位、折叠、历史恢复仍需额外控制 | 当前产品复杂度下，不建议作为唯一机制 |
| **D. 每帧平滑追踪底部** | 内容增长只更新目标，用动画逐渐滚向目标 | 可以缓和成批输出造成的大步跳动；追赶速度可调 | 有跟随延迟；用户输入与动画需要仲裁；会增加运动和逐帧工作；不能保证消除亚像素微抖 | 适合明确想要“缓缓追上”的手感，不适合直接当作此次修复 |
| **E. 正在生成区域与历史内容分开** | 当前回复在独立区域展示，完成后进入历史 | 当前区域的定位规则更简单；历史内容较少受增长影响 | 改变产品交互；完成时需要无跳变交接；跨区域选择、滚动和阅读连续性更复杂 | 只有准备调整阅读体验时才考虑，不值得仅为这次微抖采用 |

### 两个常见办法，不能直接当作替代答案

- **每次追加都调用 `scrollIntoView({ behavior: 'smooth' })`：** 只是另一种执行滚动的方式。持续变化的目标、用户打断、折叠和恢复等问题依然存在，不能替代完整的跟随策略。
- **虚拟列表：** 主要解决长历史的渲染量问题。动态高度与锚点维护还可能增加复杂度。它可以和上述方案组合，不是微抖的直接解法。

## 我推荐的 B 方案，具体会是什么样

核心不是简单拆成几个小 hook，而是明确定位优先级和写入职责。

1. **策略层回答“现在应该保持什么”。** 用户主动浏览时尊重用户；明确的跳转或发送定位执行自己的目标；折叠、恢复期间保持指定阅读锚点；普通跟随期间才保持尾部。
2. **测量层提供这一轮布局事实。** 视口、内容边界、阅读锚点和留白用同一轮几何数据计算，区分未补偿与已补偿坐标。
3. **控制器集中决定位置。** 其他功能提交定位请求，避免各自独立修改位置；同一轮更新由控制器仲裁哪些请求有效。
4. **视觉补偿独立验收。** 如果仍然需要补偿，明确补偿哪个元素、允许多大范围、何时重置。不能只要求“正在生成”不抖，而不测正文受到的影响。

这里的“集中”不意味着机械地把所有操作塞进下一次 `requestAnimationFrame`。尺寸观察与绘制时序需要实际验证，盲目延后一帧可能把原本能在绘制前完成的修正变成可见跳动。尺寸观察本身也不会因 CSS transform 而触发，因此视觉位移与布局变化不能混为一种事件。[Resize Observer 规范（工作草案）](https://drafts.csswg.org/resize-observer/)

## 关于像素精度，需要修正前面的一个表述

`scrollTop` 接口支持小数，`scrollHeight`、`clientHeight` 的接口返回整数。不能笼统地说“浏览器滚动只能取整数 CSS 像素”；具体平台的设备像素取整行为还需要实测。把函数拆开或改用另一种滚动 API，也不会自动消除这类精度差异。[CSSOM View 规范](https://www.w3.org/TR/cssom-view/#extension-to-the-element-interface)

## 实施顺序

**先用现有实现复现和定位这次微抖，再做最小修复，最后逐步迁移到 B。**

如果一开始就重写，抖动消失了也很难知道是修对了原因，还是改变了触发条件。重构收益主要是让后续行为更容易理解、测试和维护，不能提前承诺重构本身一定治好这次问题。

验收同时覆盖：底部提示的微小往返、正文同一段落的反向位移、用户上翻是否被拉回、工具卡开合、发送留白消耗，以及会话切换后的阅读位置恢复。
