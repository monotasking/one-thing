# 原子:资源 · 读 / 做 / 看(2026-09-09 方案)

> 状态:**方案,未动手**。用户 09-09 原话:「能不能更底层一点,找到一个原子点,把原子能力封装起来,给应用用、给 AI 用。」
>
> 这是 `app-intents-2026-09.md`(应用能力面)脚下的那一层。那篇说「应用自述能力,AI 读表」;本文回答「能力是由什么原子拼成的」。应用能力面在本文里退化成**一个命名空间的资源表**,它自己不再是一种机制。

## 0. 一句话

**原子 = 一个有地址的资源,加三个动词:读、做、看;「做」必须声明效果。** 会话、消息、文件、目录、歌、邮件、工作区、窗口,全是资源;AI 的工具、界面的按钮、快捷键、斜杠命令、调度任务、deeplink、CLI、插件 API、给别的 agent 的 MCP 出口,全是这三个动词在不同出口的**投影**。内核只认资源与三个动词;它不知道「音乐」「邮件」是什么。

## 1. 怎么判断找到了原子

一个东西是原子,要同时满足四条,缺一条就是「又一层抽象」而不是底:

1. **每一层都用它**:AI 用、界面用、脚本用、测试用、别的 agent 用 —— 不是只给某一个消费者的。
2. **能组合**:大的能力是小的能力拼的,拼法不需要内核知道。
3. **权限和审计有自然落点**:每一次「做」都能问「谁、对什么、什么效果」,一处问完到处有效。
4. **有地址**:能被指着说「这个」,人能指、AI 能指、链接能指。

用这四条筛今天仓库里的候选:

| 候选 | 差在哪 |
| --- | --- |
| 工具(`core/toolkit` 的 `Tool { plan → apply }`) | 只给 AI 用;界面走的是 RPC 域,两套权限、两套审计。**但它的管线是对的**(validate → intercept → plan → authorize by effects → apply → budget),原子的「做」就是它,只是要让界面也走它 |
| RPC 域(24 个,`backend/rpc/domains`) | 只给界面用;授权各写各的(09-07 留账「24 域授权迁契约」就是这条债) |
| 会话命令(`sessionCommands` 12 条) | 对了,但只覆盖会话这一种资源 |
| 事件(`events.jsonl`、EventBus) | 是「看」的原子,不是「做」的;一切皆投影这条法已经立了,原子里要保留它 |
| 应用(上一篇的能力面) | 太大:一个应用是一堆资源和动作,它是命名空间不是原子 |
| 变量(`variables`) | 是「读」的一种投影(进提示词的读),不是底 |

结论:原子不是新发明,是把已经各自存在的三样(工具的「做」、读面的「读」、事件的「看」)**架在同一个地址系统上**,让所有出口都投影自它。

## 2. 原子的定义

```ts
/** 地址。scheme = 命名空间(= 应用 id),后面是这种资源自己的路径。 */
type Ref = `${scheme}:${path}`        // session:<id>  message:<sid>/<mid>  file:<abs>  dir:<abs>
                                      // music:track/<id>  mail:inbox/<id>  workspace:<id>  window:<id>

/** 读:纯查询,无效果,可缓存。 */
interface Read<Q, R> { ref: Ref; query: Q } → R

/** 做:带效果的变更。effects 复用 core/toolkit/effects.ts 的七类;principal 是谁在做。 */
interface Do<P, R> {
  ref: Ref
  op: string                          // 'rename' | 'play' | 'send' | 'open' …
  params: P
  effects: Effect[]                   // plan 之后才知道的具体效果(带资源);上界在 OpSpec.effects
}
→ Outcome<R>                          // 复用 toolkit 的 Outcome:成功 / 拒绝 / 需要审批 / 失败,都是结构化的

/** 看:订阅一个资源(或一个前缀)上的事件流。事件是事实,不是命令。 */
interface Watch { ref: Ref | RefPrefix; after?: Seq } → AsyncIterable<Event>

/** 一种资源的自述:它有哪些读法、哪些做法、会发哪些事件。这就是「命名空间的资源表」。 */
interface ResourceSpec {
  scheme: string
  reads:  Record<string, { query: JsonSchema; result: JsonSchema }>
  ops:    Record<string, OpSpec>      // OpSpec = { params, effects(上界), home: 'core' | 'shell', when?, describe?, title }
  events: Record<string, JsonSchema>
  state?: Record<string, { volatility: 'stable' | 'turn' | 'live' }>   // 哪些读法值得主动喂给提示词
}
```

三条内核不变量:

1. **读无效果,做必声明效果,看只给事实。** 一个 `Do` 的 `plan` 阶段产出的具体效果不能超出 `OpSpec.effects` 的上界(toolkit 已经这样)。
2. **每一次「做」经过同一条管线**:校验 → 拦截(插件)→ plan → 授权(效果 × 主体 × 命名空间许可)→ apply → 审计落账 → 发事件。**没有第二条路**,界面点按钮也走它。
3. **内核不认识任何 scheme。** 谁提供一种资源,谁交一份 `ResourceSpec` + 一份实现(`home` 在 core 的交给 core 注册表,在 shell 的交给壳注册表);内核只做路由与管线。

## 4. 所有出口都是投影

| 出口 | 从原子生成什么 | 说明 |
| --- | --- | --- |
| **AI 工具** | 每个在场的 scheme 一个工具 `{ op, ref?, …params }`;一个元工具 `resources`(列 scheme、描述某个 scheme、查地址);一个兜底 `do(ref, op, params)` | 模型对具体工具准,所以主路是按 scheme 生成;兜底 `do` 让「没进面的资源」也能被点名操作(经元工具发现后) |
| **提示词** | `state` 里 `stable` 的进 system,`turn` 的进 `<context-update>` 尾块按块去重,`live` 的只在工具结果里 | = 变量系统,不另立 |
| **RPC 域** | 每个 scheme 自动得到 `read` / `do` 两个通用处理器 + 事件走既有 SSE;24 个手写域逐个退成投影 | 「24 域授权迁契约」这笔债在这里一次还清:授权在管线里,域不再各写 |
| **界面动作**(菜单 / 命令面板 / 快捷键) | 按资源聚合 ops:右键 `file:` 就列 `file:` 的 ops;命令面板列所有 `keymap` 可见的 ops | = desktop-os P1 的「一张表」 |
| **斜杠命令** | `/play` = `do(music:…, 'play')`;斜杠表从 ops 生成 | 今天的斜杠注册表退成投影 |
| **调度 / 网关 / 插件** | 都是 `Principal` 不同的 `do` | 网关审批「回 1/2/3」照旧,只是它答的是管线里的一个待授权 `Do` |
| **deeplink / CLI** | `onething://do/music:track/123/play`;`onething do music:track/123 play` | 一条语法 |
| **MCP 服务端(出口)** | 把在场的 scheme 投影成一个 MCP server,给 Claude Code / 别的 agent 用 | 这是「给 AI 用」的另一半:不只是这台的 AI,是任何 AI |
| **应用能力面**(上一篇) | = 一个 scheme 的 `ResourceSpec` + 图标 / 标题 / 作用域几格 | 上一篇整篇成为本文的一个投影 |

## 5. 位置:资源住在哪、谁跑

`OpSpec.home` 说这个做法在哪里执行:`core`(引擎进程:会话、文件、音乐、外部应用)或 `shell`(界面进程:开面板、聚焦、滚到某行、窗口)。路由规则一条:**调用方在哪不重要,资源的家在哪就去哪跑**。AI 在 core 里要 `do(window:…, 'focus')` → 管线在 core 里做完校验与授权,把 apply 那一步经 SSE 发给托管这条会话的壳,壳跑完回 RPC;没有壳就 `Outcome` 里说「这个宿主没有界面」。界面在 shell 里要 `do(session:…, 'rename')` → 经 `/api/rpc` 到 core 走管线。**两条方向,一条管线,授权永远在 core 里做**(壳不持有授权逻辑,与「宿主不判权限」的既有裁定一致)。

## 6. 什么不是资源操作(边界,比定义更重要)

不是所有点击都要过管线。判据一句话:**AI 应该能做、脚本应该能做、审计应该能看见的,才是「做」;其余是视图状态。**

| 是「做」 | 是视图状态(不过管线) |
| --- | --- |
| 重命名会话、发消息、打开一份文档、切工作区、播放、撕成浮窗、钉到架子 | 悬停、拖到一半的预览、面板滚动位置、折叠一张工具卡、输入框里打了一半的字 |
| 判据:换一个 principal(AI / 脚本)做同一件事说得通 | 判据:只有拿着鼠标的人才有这个动作 |

这条线画错的两种病:全过管线 = 每一帧一条命令,界面卡死(09-03 流式卡死那种);全不过 = 回到今天,AI 只能靠手写工具摸到一小块。

## 7. 盲点

1. **过度抽象**:「一切皆资源」是 Plan 9 的口号,它在交互式、流式的东西上会漏(PTY、语音、正在流的回复)。规矩:流式的东西是**资源 + 看**,不硬塞成读 / 做;PTY 输入是 `do(terminal:…, 'write')`,输出是 `watch(terminal:…)`。
2. **两套地址**:壳的 `ContentRef` 与 core 的 `Ref` 必须是同一套语法、同一张 scheme 表,否则又是「一种东西两个名字」。`files-root` → `dir` 这类改名一次做完。
3. **授权粒度**:效果类(七类)× 命名空间许可(设置里每个应用一格)× 主体(用户 / AI / 插件 / 调度)。三维都要,但**决定权只在管线一处**,壳不判。
4. **界面手感**:界面写操作过管线会多一次往返。既有的「写就地更新,重拉对账」(`data/kernel` 的 mutation)照旧:壳先改本地投影,`do` 的 Outcome 回来对账。管线不改这条,只是它的落点。
5. **事件账本的范围**:今天只有会话有 `events.jsonl`。原子要求每种资源的「看」都有事实来源,但**不要求都落盘**:会话落盘(已是),音乐 / 窗口这类瞬态资源的事件只在总线上,重启不回放。哪些落盘由 `ResourceSpec` 说,不由内核统一。
6. **Ref 的稳定性**:`file:<绝对路径>` 改名就变身份。接受:文件系统本来就这样;需要稳定身份的资源(会话、邮件)用 id 不用路径。
7. **投影的一致性测试**:每个出口都是生成的,所以每个 scheme 自动得到契约测试(ops 的 schema 合法、effects 在上界内、`home` 合法、每条 op 都能从 AI 工具 / RPC / 命令面板三个出口到达同一处)。这是「加功能不许改骨架」的门。
8. **模型对元工具的表现**:纯 `read/do/watch` 三个工具给模型,效果会差(要先发现再调用)。所以主路是按 scheme 生成的具体工具,元工具与兜底只是路的尽头。
9. **别把它做成框架**:内核只有地址语法、`ResourceSpec` 类型、一条管线、一张注册表、路由。任何「为了通用」加进内核的东西都先过 §1 那四条。

## 8. 陌生能力演练(法条要求)

**接一个邮箱。** 要改的文件:`runtime/src/mail/spec.ts`(一份 `ResourceSpec`:`mail:inbox/<id>` 的读法 list / get、做法 send / archive / reply、事件 received)+ `runtime/src/mail/driver.ts`(MCP 或 IMAP 实现)+ 注册表一行。之后:AI 有了 `mail` 工具、设置里有了「允许 AI 操作邮件」、命令面板里有了「发邮件」、`onething do mail:inbox/1 reply` 能用、别的 agent 经 MCP 出口能读。core 零改动,壳零改动(没有面板就没有面板;要面板再交一份描述树)。

**让 AI 把查看器滚到某一行。** `shell` 侧 `window:` 或 `document:` scheme 多一条 `home: 'shell'` 的 op `scrollTo`;壳注册表一行。AI 调 `do(document:file:/x.ts, 'scrollTo', { line: 120 })`,管线在 core 授权(效果 `silent`),apply 经 SSE 到壳。core 零改动。

两个演练的答案都是「能力自己的模块 + 各一行注册」,骨架抽到位。
