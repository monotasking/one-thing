# 学习 07：如何安全评审和推进一次架构重构

> [返回学习目录](./README.md) · [返回架构审查总览](../README.md)

## 重构成功不等于文件变短

架构重构的目标应该是让关键规则更容易证明，而不是让目录看起来更整齐。

例如把一个 4,000 行文件机械切成十个文件，如果十个文件仍访问相同全局变量，架构并没有改善，只是搜索更困难了。

## 第一步：写出不变量

不变量是任何实现都必须满足的规则，例如：

- 一个 store 只有一个 writer；
- committed 命令在重启后仍存在；
- 一个 owner 不能修改另一个 owner 的 session；
- live projection 与 cold replay 相同；
- dispose 一个 backend 不影响另一个实例。

不变量比“使用某设计模式”更重要，因为它描述的是结果。

## Characterization Test

特征测试先记录当前外部行为，不判断它是否优雅。它让内部替换实现时能够发现意外变化。

适合冻结的内容包括：

- RPC JSON fixture；
- SSE event 形状；
- `events.jsonl` 和 `meta.json` fixture；
- 错误码；
- 启动和 shutdown 顺序；
- live/cold projection 对拍结果。

如果某个当前行为本身就是 bug，应把修复前后的预期明确写进改动说明，而不是让测试悄悄改变。

## Gate 与普通测试的区别

普通测试证明某个场景能工作；架构 gate 防止依赖和调用方式重新恶化，例如：

- 新增循环依赖就失败；
- 新增模块级 locator 就失败；
- 非指定模块直接 append event 就失败；
- application import Node/HTTP 就失败。

Gate 必须有 self-test：故意放入一个违例 fixture 时应该变红。否则“0 failures”可能只是规则没有扫描到目标。

## 绞杀式迁移

安全迁移的一般形状：

```text
旧调用方 → 旧 façade → 新实现
                        ↑
新调用方 ───────────────┘
```

新实现不能反向调用旧 façade，否则形成新的环。调用点归零后才删除旧入口。

读路径可以同时跑新旧实现并比较结果；写路径不能同时提交两份，因为双写会制造新的事实冲突。

## 怎样切分一批改动

一批最好只改变一个 ownership 边界，并包含：

1. 一个明确的不变量；
2. 修复前会失败的测试；
3. 最小实现；
4. 兼容入口；
5. 门禁基线收紧；
6. 回滚方法。

不要在同一批里同时移动文件、修改协议、升级磁盘格式和改变业务语义。

## 评审时可以问的七个问题

1. 这份状态由谁拥有？
2. 谁是唯一写入口？
3. 对调用方而言什么时候算成功？
4. 进程在任意一步崩溃会怎样？
5. 重试会不会重复产生副作用？
6. 新旧实现并存时，谁是事实来源？
7. 哪个自动测试能证明边界没有倒退？

如果一个方案能清楚回答这七个问题，通常比单纯引用“六边形架构”“DDD”等名称更值得信任。
