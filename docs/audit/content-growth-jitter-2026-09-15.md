## 结论

用户补充：发生在 follow 跟随输出时，内容会有很微小的上下抖动。因此重点是跟底阶段的亚像素位置和正文锚点，不是左右晃动。

录屏已确认：跟随增长过程中，底部固定提示存在约一个视频像素的上下往返，不能因为幅度小就判为正常。

目前最值得优先排查的是 **自动贴底与整条消息的像素补偿之间的配合**。已经确认补偿代码存在一个边界缺陷，但尚未捕获抖动当时的 DOM 几何和补偿数值，因此不能把这个缺陷直接认定为本次抖动的唯一原因。

本次只做分析和只读采样，没有修改产品代码。

## 用户录屏：微小往返位移已确认

来源：[CleanShot 2026-09-15 at 15.56.46.mp4](/Users/yitiansong/Pictures/ss/CleanShot%202026-09-15%20at%2015.56.46.mp4)。视频分辨率 422 × 604，时长约 37.24 秒。

解码视频、按 30 帧/秒采样，共检查 1117 帧。选择底部不变的“正在生成”文字区域作为参照，避开持续变化的计时数字，用灰度行轮廓匹配估计竖直位移。下面的时间是采样时间，数值单位是视频像素；拟合结果保留小数不意味着测量具有千分之一像素的绝对精度。

| 录屏时间 | 相对 4.7667 秒的位置 |
| --- | --- |
| 4.7667 秒 | 0 |
| 4.8000 秒 | 约 -0.997 像素，上移 |
| 4.9333 秒 | 约 -0.996 像素，保持 |
| 4.9667 秒 | 约 +0.002 像素，基本回到原位 |

匹配后的灰度轮廓误差约 0.08–0.14 灰度级（8 位灰度范围为 0–255）。上移持续了多个采样帧。旁边块状光标的顶部也从视频坐标 y=516 变到 y=515，随后回到 y=516；光标自身亮度变化会影响阈值定位，因此只把它作为辅助证据。

这组数据支持“底部微小位置往返真实存在”，不能直接外推成“整篇正文每一块都同步移动同样幅度”。正文同时有正常向上跟随的大幅位移，仍需用同一个正文节点的实际几何量分离两者。

视频没有提供页面缩放、录制缩放和 CSS 像素的完整对应关系，因此不能把一个视频像素直接写成一个 CSS 像素。在未经缩放的 DPR=2 录制条件下，一个物理像素才对应 0.5 CSS 像素；这里只作条件说明，不当作已经量出的页面幅度。

**当前结论分两层：抖动现象已确认；具体是哪一段逻辑造成，仍需要开启/关闭补偿的同内容重放对照。** 对这个问题，不应设定“达到 1 CSS 像素才算抖动”的门槛。

## 已确认的行为

### 1. 内容长高会触发整个内容区重新滚动到底部

`apps/desktop-react/src/content/ChatStream.tsx:1498` 判断内容是否长高或容器是否改变；跟底状态下、底部留白消耗完后，在第 1561 行调用 `stick()`。

`ChatStream.tsx:1018` 执行 `el.scrollTop = el.scrollHeight`，随后在第 1028 行执行 `snapTail(el)`。

因此，底部增长会带动前面已经显示的内容向上移动。单向移动是当前跟底设计的正常结果；需要查的是方向反转、突跳或文字反复发虚。

### 2. 所谓“尾部补偿”实际移动整条回复

`ChatStream.tsx:983` 取内容列最后一个子元素；如果它是留白垫块，就取前一个。第 1001 行直接写入该元素的 `style.translate`。

运行中页面的 DOM 证实目标是 `ARTICLE`，采样到的两条回复分别带有：

- `translate: 0px -0.765625px`
- `translate: 0px -0.554688px`

所以补偿的影响范围包括整条消息里的正文、思考内容和底部提示。该行为本身不等于已经证明抖动：补偿也可能抵消原有的滚动误差，必须做开关对照。

### 3. 补偿算法违反“只能向上挪”的约束

`apps/desktop-react/src/content/tail-snap.ts:90` 的 `resolveTailSnap()` 在自然位置离旧落点不超过三个设备像素时，继续使用旧落点，却没有保证新补偿值小于等于零。

直接执行当前源码函数，在设备像素比为 2 时得到：

| 自然下缘位置 | 保持的落点 | 补偿位移 | 是否重选落点 |
| --- | --- | --- | --- |
| 632.2 | 631.5 | -0.7 | 是 |
| 631.3 | 631.5 | +0.2 | 否 |
| 632.2 | 631.5 | -0.7 | 否 |

第二步发生了向下补偿。这是确定的算术反例。文件头第 38 行明确依赖“只能向上”来避免扩大滚动范围，但函数没有落实这个约束。

实际是否因此扩大滚动范围、引起再次贴底，取决于元素位置、留白和裁剪等布局条件；本次没有证明现场已经出现了这条反馈链。

## 为什么已有测试可能漏掉

- `apps/desktop-react/scripts/gate-send-flow.mjs:1108` 的流式反转检测读取的是 `readout.top`，主要保护底部“正在生成”提示。它不能单独证明正文中固定段落也稳定。
- `apps/desktop-react/scripts/gate-stream-monotone.mjs:235` 采样的是文字长度。字数不减少，并不保证排版高度不减少或屏幕位置不反转。
- `apps/desktop-react/src/content/__tests__/tail-snap.test.ts` 有“位移永远小于等于零”的测试，但输入只在较窄区间摆动，没有覆盖上表的反例。

## 现场采样的边界

当前应用设备像素比为 2。连续约三秒、359 帧的只读采样中，两块会话的文字长度和内容列高度都没有增长。一块完全静止，另一块只有滚动位置变化。因此这段采样可以确认补偿挂载位置，但不能复现用户描述的增长抖动，也不能把当时的滚动变化归因于程序。

本机没有可用的 browser-use 命令，随后通过应用已有的本地调试接口完成只读 DOM 采样。

另外跑了一个独立 Chromium 最小实验：用分数行高的文字逐帧增长，复现当前贴底加整条消息补偿的计算。在已跟底的 162 个采样帧里，正文向下反转 0 次，底部位置变化范围为 0。实验没有复现上下往返，因此“有分数像素 + 整条消息 translate”本身不足以解释本次症状；还需要真实内容布局变化或时序条件。这个结果也说明不应直接删除补偿后宣称已修复。

## 下一步如何判定真正原因

在独立测试会话里重放同一段持续增长内容，同时记录：滚动位置、整条消息高度、补偿位移、正文中同一个固定段落的屏幕坐标，以及底部提示坐标。

1. 对比开启和关闭 `snapTail`：若正文往返位移或发虚显著减少，而底部提示恢复轻微抖动，就能确认补偿范围或策略存在问题。
2. 若消息高度先缩后长，应追查流式内容分块、换行或折叠造成的布局变化。当前观察器第 1498 行会跳过单纯缩高的情况，需要结合浏览器自动限制滚动位置的行为一起检查。
3. 若高度稳定但滚动位置往返变化，再核对滚动锚定、留白更新和程序主动滚动的时序。

修复时应先补上正位移反例，并把“固定正文段落不得反向跳动”加入真实渲染测试。不要仅凭底部提示稳定，就认定整条回复已经稳定；也不要未经对照就直接移除现有补偿。
