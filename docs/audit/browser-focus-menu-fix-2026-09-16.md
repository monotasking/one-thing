# 浏览器焦点与菜单修复

## 结果

已实现方案 B：修复应用外壳与原生网页之间的焦点交接，并将浏览器 `⋯` 菜单改为系统原生菜单。主进程和 preload 均有改动，需要完整重启应用才会生效；仅刷新页面不能加载新菜单能力。

独立测试窗口中，地址栏单击、⌘L、Escape，以及菜单中的“把这一页交给对话”均验证通过。菜单打开时网页保持显示，不再经过截图替换。

用户报告的“网页顶部有一片区域无法点击”仍未稳定复现，不能标为已修复。后续需要在具体页面与窗口布局下检查该区域的原生视图边界、拖拽区域及遮挡状态。

## 改动与原因

### 焦点交接

原先网页报告自己获得焦点时，外壳更新焦点树又发出一次网页聚焦请求。窗口恢复旧的原生占位格焦点时也会触发这条路径，导致地址栏刚获得焦点便被网页抢回。

现在将“收到焦点事实”和“主动请求焦点”分开：原生通知只更新焦点树，不再回发聚焦命令。显式焦点请求带递增版本，更新的地址栏或外壳交互会取消排队中的旧网页聚焦请求。隐藏或被遮挡的网页不会被程序重新聚焦。

实际测试还发现，网页内按 ⌘L 时，DOM 输入框获得焦点并不等于系统把键盘交给外壳。已补上显式交接，覆盖地址栏和页内查找输入框，以及焦点树的程序化焦点切换。

### 菜单层级

浏览器动作仍由渲染层的一份动作表定义。桌面环境将标签、可用状态和动作 ID 交给 Electron 原生菜单，关闭后通过请求编号回传一次选择，再执行原来的业务回调。菜单打开期间取消排队中的焦点变更，关闭时不重放旧请求。

原生菜单不再注册 DOM 遮挡层，也不触发截图、隐藏网页、再恢复网页的流程。没有原生菜单能力的环境继续使用原有 DOM 菜单。

代价是菜单外观和键盘交互遵循操作系统；菜单展示的是打开时的动作快照。浏览器身份设置在浏览器叶片挂载时预先读取，后续打开菜单沿用缓存。

### 实际桌面交互

使用独立数据目录启动完整应用，并通过本地测试网页验证：

- 从网页输入框单击地址栏一次，地址栏保持焦点；系统焦点确实转到外壳。
- 从网页按 ⌘L，地址栏获得系统焦点且选中完整地址。
- 地址栏按 Escape，焦点返回网页。
- 打开 `⋯` 后出现系统原生菜单；原生网页仍可见，DOM 菜单及截图占位数量均为零，未发送遮挡请求。
- Escape 关闭菜单，焦点回到触发按钮。
- 用方向键和回车选择“把这一页交给对话”，对应页面引用进入输入框，未发送消息。

测试没有覆盖所有网站、其他操作系统、真实切换到另一应用后再返回，以及原生菜单的多身份选择。相关状态与业务逻辑有单元测试覆盖，但不能替代这些实际场景。
