## 结论

用户关于层级、焦点的判断有实测支持，但目前不能把三个现象全部归为同一个缺陷。

| 现象 | 调查结果 | 确定程度 |
| --- | --- | --- |
| ⋯ 菜单先被网页覆盖，闪一下才浮出来 | 菜单先挂载；之后等待网页截图，再隐藏原生网页；截图在外壳中还需要解码和下一帧才能显示。切换存在两个可见时间窗口。 | 代码与运行时顺序均已确认 |
| 地址栏需要点击多次 | 单击已命中地址栏并获得焦点，随后网页重新夺回焦点。原生视图与外壳之间的双向焦点同步会产生回送。 | 连续两次单击复现，并捕获到程序置焦调用栈 |
| 网页上方一片区域无法点击 | 当前中央区 Gemini 的顶部侧栏按钮能够收到完整点击事件并展开；未复现用户描述的固定不可点击区域。 | 待补充具体页面、位置及中央区/侧栏/浮窗场景 |

建议优先处理焦点回送和菜单显示交接；顶部不可点击区域仍应保留为独立问题，不能据本次局部成功宣布已排除。

## 1. 菜单为什么先遮挡再闪烁

网页通过原生 `WebContentsView` 承载，菜单则属于外壳的 DOM。两者不是同一个 CSS 堆叠上下文。代码用“原生网页 → DOM 截图”的交接来让外壳菜单显示在网页上方；单独提高菜单的 `z-index` 无法完成这个交接。[Electron 的 WebContentsView 文档](https://www.electronjs.org/docs/latest/api/web-contents-view)说明了该视图由主进程创建并加入窗口的视图树。

当前过程：

1. 点击 ⋯，React 挂载菜单及焦点作用域。
2. `NativeViewSlot` 订阅到焦点树变化，在下一动画帧计算遮挡，发送 `occlude`。
3. 主进程等待 `capturePage()`，完成后才隐藏原生网页并推送截图。
4. 外壳收到截图，插入初始隐藏的图片；等待图片解码及动画帧后才显示。

本次运行时记录，以菜单 DOM 出现为 0：

| 相对时间 | 观察 |
| --- | --- |
| 0 ms | 菜单已在 DOM 中，尚无截图 |
| +14 ms | 收到网页的原生焦点通知；此前菜单已失去窗口内焦点 |
| +112 ms | 收到原生网页失焦通知 |
| +116 ms | 收到截图推送 |
| +119 ms | 截图元素插入，但仍隐藏且未加载完成 |
| +158 ms | 截图开始显示 |

所以菜单出现后仍有一段时间原生网页留在上层；原生网页隐藏后，截图尚未准备好，又有短暂衔接空档。这里记录的是事件时间，不是逐帧像素测量；116/42 毫秒是该次操作的样本，不是固定延迟。

## 2. 地址栏为什么点中了仍没反应

本次两次单击地址栏，都在外壳收到完整 `pointerdown → mousedown → focusin → mouseup → click`。因此这两次不是点击被透明遮罩挡住。

第二次记录，以地址栏的 `pointerdown` 为 0：

| 相对时间 | 观察 |
| --- | --- |
| −4 ms | 外壳恢复焦点，之前激活的原生视图占位元素收到 `focus/focusin` |
| 0 ms | 地址栏收到 `pointerdown` |
| +2 ms | 地址栏收到 `focusin`，外壳确实拥有焦点 |
| +13 ms | 地址栏收到 `click` |
| +15 ms | 地址栏失焦，外壳 `document.hasFocus()` 变为 false |
| +86 ms | 程序再次调用原生视图占位元素的 `.focus()` |

最后一次程序置焦的调用栈明确来自：

`NativeViewSlot 收到 focus 通知 → useFocusScope.activate → FocusTree.activate → 占位元素.focus()`。

代码形成了双向回送：

- 占位元素收到 DOM `focus`，就向主进程发送网页 `focus` 命令。外壳重新成为第一响应者、恢复先前激活元素时，也可能触发这条路径；命令会在本次鼠标点击处理期间排队。
- 主进程的网页 `focus` 通知回来，外壳调用 `activate('pointer')`；这个方法不仅更新焦点树，还实际调用浏览器默认落点的 `.focus()`。
- 对已有 URL 的浏览器，默认落点是网页占位元素。该通知没有标记焦点请求来源或版本，也不判断用户是否已经把焦点移到地址栏。

这解释了实际观察到的“刚进入地址栏，又回到网页”。其中最早的原生焦点请求没有直接拦截主进程 IPC，本次依据 DOM 恢复事件、代码发送路径与后续通知关联；不把它描述为已经记录到主进程的完整调用栈。

## 3. 网页上方不可点击：当前证据与边界

当前中央区测量：外壳视口为 1280 × 860，地址栏输入区位于 y=53–79；网页容器为 x=0、y=90、1280 × 770，网页内部视口也为 1280 × 770。

外壳命中测试在地址栏中心返回输入框，在 y=90、100、120、140、180 返回原生视图占位元素，没有发现额外 DOM 遮罩。这个测试只能观察外壳 DOM，不能单独证明原生视图的窗口命中区域正确。

实际点击 Gemini 顶部 `Open sidebar`，网页收到坐标约 (26, 28) 的完整鼠标事件，侧栏成功展开；之后已还原。该点验证了网页顶部至少一处可以点击，不能代表横向整条区域或其他网站。

还有一条需要留意的代码路径：任意 `float/modal` 作用域会让可见原生网页整体转为截图，而截图不具备网页交互能力。若菜单状态或遮挡状态残留，会呈现“看得见但点不动”；不过这解释的是整片视图，不能直接解释用户描述的仅上方区域。

已向用户询问具体页面、位置以及中央区/侧栏/浮窗场景；尚未取得该定位信息。下一步应在问题现场同时记录外壳命中、网页鼠标事件、原生视图矩形及遮挡状态，确定点击在哪一层消失。

## 4. 修复方向与验证要求

### 焦点：区分通知与主动转移

原生网页的焦点通知应同步逻辑归属，避免无条件再下发原生聚焦。外壳恢复先前占位元素时，也不能覆盖用户随后点击地址栏的意图。需要记录请求来源/新旧顺序，并在菜单等捕获焦点的界面存在时拒绝旧网页请求。

验证应覆盖“网页 → 地址栏单击”“网页 → 菜单”“从其他应用返回后单击地址栏”，并延后投递旧 focus 通知，确认输入框或菜单持续持有焦点。

### 显示：把菜单、截图、原生网页的交接协调起来

应让截图准备完成、原生网页隐藏、菜单呈现成为有完成确认的交接过程，并处理截图失败和恢复网页绘制的路径。不能只把隐藏提前，否则可能把遮挡改成更长的空白。浏览器自身的 ⋯ 菜单也可评估使用原生菜单，但全局 DOM 弹层仍需解决共同交接问题。

验证需要真实 Electron 窗口的连续画面与鼠标操作；DOM 测试不能验证跨原生视图层级。
