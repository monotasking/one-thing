> 结构债 S 线第一期(`docs/design/structural-debt-plan-2026-08.md` 「08-24 I4-缝收口」)。
> **本文档是盘点,不是改动。** S1 只产出这份表;S2(补 `implements`/显式标注)、

## 1. 审计方法

**数据不是 grep 出来的,是 TypeScript 类型检查器算出来的。** 复现脚本三段(一次性,未入库,见 §1.4):
以 `tsconfig.node.json` 建 `ts.Program`(2190 root files / 2920 source files),拿 `TypeChecker`,
然后三遍走 AST。

### 1.1 什么算一道"缝"

**population = `packages/core` 与 `packages/onething-runtime/src` 里,所有 `export` 的
interface / 字面量 type alias,且成员里有函数(方法签名,或属性的类型是函数类型)。**

初筛得 **682** 个。再按"是不是行为端口"收一刀:

- **入表**:成员全是函数(`allFn`),**或**函数成员 ≥ 2 个 → **516 个**,就是下面四张表的全集。
- **不入表**:只有 1 个函数成员且其余全是数据字段(`{ id, name, onDone }` 这类回合载荷)→ **166 个**,
  纯数据形状,按任务口径跳过且不进表。

516 个里再分两类(表里的 `方法数` 列不区分,判定口径区分):
- **角色口 `role`(297)**:有人**持有**它并反复调它(字段/属性/变量类型)。
- **参数包 `bag`(219)**:名字以 `Options|Config|Params|Args|Init` 结尾,或全仓每一处引用都只是
  `param` 位置 —— 它是**一次调用的形状**,不是一个协作者。参数包被多处调用**不算变化轴**
  (七个调用点填同一个 options 不是七个实现)。

### 1.2 "生产实现"怎么找到的 —— 三种,鸭子口靠 contextual type

tsserver 的 Go to Implementation 只认前两种;第三种正是病灶。表里的实现列用标记区分:

| 标记 | 含义 | gi 认吗 |
| --- | --- | --- |
| `**implements**` / `**class-extends**` / `**satisfies**` / `**iface-extends**` | 声明了边 | 认 |
| `**named-const**` / `**factory-return**` / `**assign**` | 对象字面量赋给具名 const / 从工厂 return / 赋值 | 部分认(带类型标注才认) |
| `inline-arg` / `inline-prop` | 对象字面量**就地**写在调用参数 / 属性值里(靠 contextual type 认亲) | **不认** |
| `duck:<Class>` | 传进去的是一个**已有对象**(标识符/调用返回值),它结构上满足这道口 | **不认** |

`duck:` 行的 `file:line` 指向**那个已有对象的声明处**(真正的实现体),不是传参处。
样例(病历原文那一条):`CoreSessionCommandEmitterLike`(`packages/core/events/ipc-operations.ts:15`)
唯一生产实现是 `packages/backend/events/event-bus.ts:8` 的 `EventBus`,经
`packages/backend/rpc/domains/session-command.ts:183` 的 `getEventBus()` 传入 —— 全仓零 `implements`,
gi 返回空,只有类型检查器看得见这条边。

### 1.3 各列口径

- **方法数**:`n` = 成员全是函数;`n/m` = m 个成员里 n 个是函数。
- **生产实现**:排除 `__tests__` / `__mocks__` / `*.test.ts` / `evals/` / `scripts/`。最多列 4 条。
- **调用者数**:**生产文件**数,该文件在类型位置(param / prop-sig / field / var-annot / return-type /
  alias / 成员)引用了这道口,且不是实现文件本身、不是声明文件本身。
- **变化轴**,机械判定,四种之一或组合:
  - `多实现(N 处命名实现)` —— 有 ≥2 个具名实现体。
  - `多接线点(N 文件各自构造)` —— 没有具名实现,但 ≥2 个文件各自就地构造(多宿主各自接线)。
  - `跨层注入(X←Y)` —— 口声明在 X 层,实现落在 Y 层(产品 ← 装配/宿主)。
  - `可缺席(optional/nullable)` —— 这道口在某处是 `?` 或 ` | null`,缺席 = 该能力不存在。
- **gi**:`通` = 存在 `implements`/`extends`/`satisfies`,或存在**带类型标注的变量/字段**声明。
  `**不通**` = tsserver 的 Go to Implementation 今天返回空或只返回声明本身。
- **判定**:
  - **留+补边** —— 有真变化轴但 gi 不通 → S2 补 `implements` / 显式标注。
  - **留(已通)** —— 有变化轴且 gi 已通 → S2 不动。
  - **删内联** —— 无变化轴、单实现、调用者 ≤ 1 且同层 → S4 改直接类型引用。
  - **另册** —— 零实现 / 零消费 / 单实现多消费,见 §6,一条一句现状,不判。

### 1.4 复现

四段脚本按顺序跑(需 `node --max-old-space-size=8192`,单次全程约 4 分钟):
建 Program → 收口 + 三遍 AST(implements / contextual-type 对象字面量 / contextual-type 标识符供体)→
回读对象字面量的语法槽位(具名 const vs 就地参数)→ 扫全仓 `export function configure*` 及其调用点。
脚本是一次性产物,**没有入库**:S1 的交付物是这张表,不是一个新的门。要复跑就照 §1.1–§1.3 的口径重写,
口径本身在这里,不在脚本里。
