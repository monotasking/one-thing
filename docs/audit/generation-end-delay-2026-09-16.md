# 正文结束后仍显示生成中：定位与修复

## 结论

**这次模型早已结束，界面漏收了完成事件，又没有在重连后主动核对状态。** 因此一直等到约 45 秒后的下一条会话事件，才恢复为完成状态。

## 触发链路

1. 收尾会广播整条助手消息，包括思考、正文、工具调用及步骤。
2. 用该会话账本重建收尾前的消息，生成的更新信封为 **2,339,674 字节**；推送队列总预算为 1,048,576 字节，实际数据预算还扣除了控制帧预留。
3. 把这份真实数据重建的更新交给现有 `createSseDelivery`：更新被拒绝，发送 `transport:resync-required` 并结束连接；随后的完成事件也无法写入这条已关闭的连接。
4. 客户端默认订阅全部会话。服务端这条订阅分支没有按 `after` 补发历史事件，重连本身不会补回完成事件。
5. 聊天数据源原来只在收到后续账本事件、发现序号不连续时核对。没有新事件就一直保留旧的“正在生成”。本次下一条恰好晚了约 45 秒。

证据边界：第 2、3 步是使用真实账本和现有生产函数的确定性重建，并非原连接的网络抓包。原始事件和连接关闭时刻支持这条因果解释；不把重建数据说成已经抓到的原始网络包。

- [chat-port.ts](/Users/yitiansong/data/code/start-electron/apps/desktop-react/src/data/chat-port.ts)：连接恢复时通知数据源，不等待新连接上的第一条事件。

这修复了“漏掉完成事件后一直等下一条事件”的缺口；未改变推送层的大小限制，也未移除收尾的大消息广播。发生断线时仍有重连及读取状态的耗时；已有核对节流窗口为 3 秒，不能承诺任何网络条件下都瞬时收尾。
