# 流式几何引擎(G 线,2026-09-20 设计)

起因:用户 09-20 报三件事 —— 发送后屏上有两处「在等」的动画;头部那道消失时布局上下变化;思考段想完自动收起,正在读的人被打断。随后提出要一个排版 / 渲染引擎,五条要求:

1. 引入块级处理:后面的块折叠或收缩,不影响前面块的位置;
2. 块可扩展(工具调用等),且遵循自动跟随的规则;
3. 允许流式时不展开,用动画表示它正在生成(例如思考段);
4. 流式渲染是增量渲染,不对历史做完整重渲;
5. 流式结束时不错位、不重排;元素在流式中只要落在屏幕上,位置就确定了。

R 线(`stream-render-2026-09.md`)管的是「**画什么**」:内容只增不换、块身份稳定、DOM 不重挂。「**画在哪**」一直没有负责方,今天由五个互不认识的补丁各管一角:`content/follow.ts`(跟底)、`content/seat.ts`(发送后的座位垫块)、`content/tail-snap.ts`(尾部亚像素对齐)、`content/fold-intent.ts`(折叠时钉视口)、`content/expand-intent.ts`(点开时别贴底)。每个补丁治好自己那一种跳法,下一种还会来。G 线立的是几何那一半的宪法,并指定唯一的负责方。

## 1. 五条几何不变式(宪法)

**G1 · 后块变矮,屏上其余不动。** 文档流里后块收缩本来就不改前块的文档坐标;让前面跳的是贴底时页面总高变小、浏览器钳 `scrollTop`。所以:**一轮之内页面总高在任何一次排版里都不许变小**。手段是卷尾垫块(§3.3):任何块缩掉的高度记进垫块。

**G2 · 收缩先申请、后执行。** 今天的病根是顺序:块自己先缩,引擎事后补救,而钳位发生在中间那次排版里。规矩:块向引擎申请「我要缩」→ 引擎从几何账本读出缩之前的高度、先把垫块加长 → 块再缩。「量改后多高」这类会逼出排版的读取,只许引擎在垫块到位之后做。

**G3 · 块有直播形,自动收缩不存在。** 每种块声明流式期间的形:`grow`(跟着内容长,如正文)/ `fixed`(高度恒定、里面在动,如思考段)/ `reserve`(先占形、内容后到,如图片、公式)。块的高度在流式期间只增不减;会变矮的只有一种原因 —— 用户自己点的。

**G4 · 落定那一帧几何上什么都不发生。** 收尾只许换透明度、颜色、停动画,不许换高度。只在流式期存在的东西必须住进**槽位**:从头到尾都占着的固定格子,内容只换 `opacity`。

**G5 · 上屏即定位。** 定的是相对这一轮起点的**文档坐标**。屏幕上只允许一种运动:贴底跟随时整体匀速上移。此外任何东西都不许动。

推论五条(引擎必须回答):

- `scrollTop` **只许一个写者**(锚定器,§3.2);块不许碰滚动,只报几何变化。
- **用户主动展开 / 收起**:被点的那一块顶边不动,只有它下面的让位。
- **事后才出现的行**(上下文更新行、收场通知、来源脚注):要么进槽位,要么只许出现在尾部。
- **整体重排**(拖窗口、开关侧栏):以视口里第一块的顶为读者锚点恢复位置。
- **执法**:真机门 `gate:stream-geometry`(必须含**短会话**场景)+ dev 运行时断言「上过屏的活动块高度不许变小,除非原因是用户」。

## 3. 结构(都是现有件的收编)

### 3.1 一轮回复的排版

```
[用户气泡]
[上下文更新行]          ← 事后行,只在这一轮开张时出现一次
[活消息 article]
   [块 … 块(frozen)] [活动块(live)]
   [动作格]             ← 常驻,流式中 opacity 0 + inert
[卷尾垫块]              ← 座位 + 吸收的回缩
[尾槽]                  ← 整列常驻的一格:等待扫光 / 光标 + 读数 + 停止;不在跑时透明
```

只有**槽位**和**块**,之间不许条件渲染别的东西。

### 3.2 锚定器(`ViewportAnchor`,P2)

收编 `follow` / `seat` / `tail-snap` / `fold-intent` / `expand-intent`。所有几何变化报给它:

```ts
interface GeometryChange {
  blockId: string
  deltaH: number
  cause: 'tail-growth' | 'user-toggle' | 'late-insert' | 'settle'
}
```

裁决:视口下方 → 不管;视口上方 → 补偿 `scrollTop`;视口内 `tail-growth` 且贴底 → 跟随;视口内 `user-toggle` → 钉住被点那一块的顶;其余 → 违例(dev 报错)。

### 3.3 卷尾垫块(P2)

现有座位垫块的升级:`height = max(座位所需, 本轮已吸收的回缩)`。释放时机:用户滚动、下一次发送。

### 3.4 段注册表与几何契约(P3)

正文块已经是「自述 + 注册表」(`blocks/registry.ts`,五问流式契约里已有 `geometry: 'flow' | 'reserve'`)。段这一层还是枚举:`SegmentView.tsx` 的 `switch(kind)` 与 `assemble/index.ts` 的 `switch`。按仓根「加功能不许改骨架」法,两处都改成读表:

```ts
interface SegmentDef<M> {
  kind: string
  produce(part: ProjectedPart, prev?: M): M
  View: ComponentType<{ model: M; ctx: BlockCtx }>
  stream: BlockStreamContract          // 现有五问,原样
  geometry: {
    liveForm: 'grow' | 'fixed' | 'reserve'
    settle: 'same-height'              // 只有这一个合法答案,写出来是为了必答
    shrink: 'never' | 'user-only'      // 没有「自动」这一档
  }
}
```

**陌生能力演练**:加一个没想过的块(AI 生成的 HTML 预览)。要改的 = 它自己的模块(`produce` + `View` + 契约,`liveForm: 'reserve'`)+ 一行注册。跟随、垫块、落定不跳都不用它操心。前提是两个 `switch` 真的删了。

### 3.5 冻结线与几何账本(P4)

块只有 `live → frozen` 两态,单向。冻结之后不再量高、不再重渲;高度记进账本,交给 `content-visibility` 当占位高。三份 `HeightBook`(`ui/flip-height` 通用 / `tools/card-heights` / `thought-heights`)合成一份,按块 id 记 {高度, 首次上屏时刻, 是否冻结},同时喂锚定器、占位高、dev 断言。每帧工作量只跟活动块有关,由 `gate:perf` 守。

## 7. P1 施工账(2026-09-20)

止血三件与那道几何门都落了地。**与 §5 设计不一样的地方以这一节为准**,逐条写明为什么。

### 7.1 与设计不一样的六处

1. **座位必须与内容**同帧**改,不是「量在这一帧、写在下一帧」**(设计里没有这一条,
   是这道门第一趟真机挖出来的)。座位从前走 `FrameCoalescer` 下一帧写,于是每来一段
   delta:第 n 帧内容 +Δ、座位没动 → `scrollHeight` +Δ;第 n+1 帧座位 −Δ → 回来。
   **屏幕上从前看不出来** —— 读数行那时住在正文**里面**,跟着内容一起往下走,那一格差
   被它自己的位移盖住了(正是 §0 的病 ④)。P1 把读数与光标搬到**座位之后**,这一格差
   当场显形:首字那一帧尾槽被推下 **29–92px**(= 第一块内容的高),整轮 `scrollHeight`
   回缩 **3–15 次**。
   一帧之内两头不能兼得(不动视口 → 座位**下面**的跳;贴底 → 座位**上面**的跳,自己那条
   气泡当场违反 `send-flow` 规矩 ②),唯一的出路是**让那一格差不存在**。所以
   `ChatStream` 多了一只 layout effect:座位在场且还没吃光时,在 React 提交之后、绘制
   之前同步 `readSeat` + `writeSeat`。它是 §1 的 G2「收缩先申请、后执行」在 P1 能做到的
   那一半(完整的两段式归 P2 的锚定器)。
   三道闸让它不重演 09-10 那只「每次提交都 `stick()`」的 834ms:座位不在场 / 座位已吃光 /
   正在滑(发送与重试的插值),任一命中立刻返回。**反证**见 7.3 第一行。
2. **等待那道折痕不是「新画一件」,是 `WaitingSeam` 换了住处**。§5.2 写的是「复用折痕
   基座的 `SeamLine`」,实现上直接消费了 `content/seam/WaitingSeam`(它的自述本来就是
   「一道没有标签的、在扫的折痕」),只删掉它那句 `min-height`(高度归宿主那一格 token)
   并改写文件头。理由是仓根第一条:**组件化而不是创建新的组件**;任务单里那句
   「确认零消费者后删」是个条件句,而它今天有一个消费者。
3. **尾槽里的三张脸,空着时那两张不挂载**。§5.2 说「三张脸同格只换 opacity」——
   几何上那句话由 token `--tail-slot-h` 兑现(与此刻是哪张脸无关),而**在跑**时两张脸
   确实同格、交叉淡入、暗的那张 `inert`;**不在跑**时两张都不挂载。因为那道扫光与那枚
   光标是两段 `infinite` 动画,一片会话叶一份,而一台上可以并排开好几片 —— 空着时挂着
   是白烧,而几何一格都不多给。
4. **收起态那一行的高由 `block-size` 钉死,不靠两态恰好一样高**。§5.1 只说「两态高度
   逐像素相同」;实现上不敢把它交给内容(流式那一截右端对齐、落定那一截左起 + 省略号),
   所以 `.thoughtPreview` 直接 `block-size: calc(var(--fs-meta) * 1.6)`。
   右端对齐那一手也比设计多一句:`justify-content: flex-end` **加** `flex: none`
   —— 只写 `margin-inline-start: auto` 不成立(自动外边距只吃**剩余**空间,而这里
   剩余是负的,它当场解析成 0)。

### 9.1 量法(`scripts/probe-tail-jitter.mjs`,新件)

手感类报障禁纸上诊断,所以先立一只**只量不判**的探针。三条纪律:**dpr 钉 2**
(CDP `Emulation.setDeviceMetricsOverride`;`tail-snap` 的整套判据以设备像素计,
dpr 不对结论就不对,门起来第一句就核对 `window.devicePixelRatio`)、**每帧 O(1) 且
一次 `getComputedStyle` 都不许有**(`translate` 读产品自己写的**内联**样式;09-10
「探针自伤」判例 P1b 刚又踩过一次)、屏外档 + 临时 store,收尾收尸自查。

逐帧记:尾槽 `rect` 的 top/bottom(留小数)、它的内联 `translate`、`scrollTop` /
`scrollHeight` / `clientHeight`、列的**分数**总高与下缘、座位高、停止钮与读数那一行
的 rect 与文字、以及一块钉住的正文当锚。导出:取值集合与各值帧数、帧间 Δ 直方图、
方向反转、峰峰值(px 与设备像素)、每秒变化次数、**一帧滞后**(同一帧 `gap > 一个设备
像素`)、`translate` 变化序列,外加横向那一把尺(读数那行字的左缘与宽)。

三个场景(`text` / `think` / `tools`)× 两种规模(空会话 / **真店夹具 50.9MB · 400 条**,
`--big`)。**规模是这一单的胜负手**:小会话上三个场景全都量不出抖(峰峰 0.008px),
真店规模上当场出来 —— 这也正是 P1 / P1b 那十二条门一路全绿却没接住用户的原因。

### 9.2 读数:抖的是**两种**,不是一种

真店规模 · `text` 场景 · dpr2 · 贴底跟随 7–8 秒,尾槽 `top`:

| | 峰峰 | 设备像素 | 方向反转 | 变化次数 | 取值集合 | 一帧滞后 |
| --- | --- | --- | --- | --- | --- | --- |
| **现版 main** | **2.516px** | **5.03** | 1 | 17 / 2.1 次每秒 | 17 个 | 6–8 帧(1–2px) |
| (a) 拆掉 `snapTail` | 2.672px | 5.34 | **42** | **79 / 9.6 次每秒** | **58 个** | 8 帧 |
| (b) 候选 A(sticky) | **0.234px** | **0.47** | 9 | 15 | 11 个(887 帧同一个值) | 7–8 帧 |

小会话(同一份代码、同三个场景)全部是 **0.008px / 反转 1 / 取值 2 个**。

两种抖,拆开看:

- **① 亚像素连续抖** —— 反证 (a) 把它放了出来:拆掉 `snapTail` 之后反转从 1 跳到 42、
  每秒变化 9.6 次、取值 58 个。**09-15 的 `content/tail-snap.ts` 治的就是它,今天仍然
  在治**,所以这一件**不能退役**(候选 A 落地之后再拆一次,反转 9→31、变化 15→46、
  取值 11→23 —— 比留着差,判定:留)。
- **② 慢摆** —— main 上那 17 个取值里有 14 个**只出现一帧**,而且连起来是一条
  `553.117 → 553.25 → 553.398 → … → 555.008` 的**单调斜坡**(每帧 0.13–0.34px,都不到
  一个设备像素),走完约十帧再一次弹回 552.5。峰峰 2.5px = **5 个设备像素**,约两秒
  一个来回。**这就是用户说的「幅度很小的上下滚动」**,也是「鼠标放上去能看出这个元素
  的位置确实有些变化」那一句 —— 停止钮 `top` 与尾槽逐帧同值,悬停底色一亮就看得见。
  `tail-snap` 治不了它:它补的是「内容此刻在哪」与「设备像素格在哪」之差,而这一段
  里那个差**本身**在慢慢漂。

用户的第二问(上面的正文抖不抖)**答案是抖,但不是来回抖**:锚点 63 次移动里
**往回走 0 次**、步长与内容增量对不上 4 次;而「残值」(视口下缘 − 列下缘)峰峰
2.1–2.7px、**56–59 个取值** —— 也就是说正文每长一截就落在一个**不同的亚像素相位**上,
文字跟着重新栅格化。那是滚动本身的性质(落点只落得到设备像素格上,09-15 §11.1 已经
量过),不是这一单引入的,候选 A 也**不动它**(A 只改尾槽的坐标系)。

横向那一把尺全程 **0px**:读数那行字的宽度 925 帧里只有一个值(91.25),
「数字每 100ms 换一次导致整行左右挪」这条假设**当场被证伪**。

### 9.3 裁决:候选 A(sticky),`tail-snap` 留着

治法不是再算得准一点,是**换一个坐标系**:跟随态下尾槽的位置由**滚动口**说了算,
不由内容流说了算。

```css
[data-follow='pinned'] .slot { position: sticky; bottom: 0; }
```

`ChatStream` 的滚动容器多一格自述 `data-follow={follow.mode}`(跟随状态机本来就有的
那一格,不新开状态)。三条判词写在 `TailSlot.module.css` 那一节上:只在 `pinned` 时
生效(人往上翻历史时必须回普通流,否则它会浮在屏底盖住正文 —— 那是另一个产品决定,
本单不做)、`bottom: 0`、自然位置 ≡ 粘住位置。

**`bottom` 那一格踩过一次,留成判例**:第一版写的是
`bottom: calc(var(--composer-h) + var(--composer-gap))`(照着滚动容器的
`padding-block-end` 抄),真机量出来尾槽比自然位置**高了整整 141px**(552.5 → 411.5)。
原因是粘性的参照不是滚动口的 padding box 本身,而是它**再减去 `scroll-padding`**
之后那一块,而 `.scroll` 早就写着同值的 `scroll-padding-block-end` —— 让位已经在参照
里减过一次,这里再写就是减两遍。**粘性的 `bottom` 与滚动容器的 `padding-block-end`
不是一件事,中间隔着 `scroll-padding`。**

`tail-snap.ts` **不退役**(与派工单的设想相反,由读数裁决):它治的是抖 ①,而 A 治的是
抖 ②,两件事。A 落地后再拆一次 `snapTail` 的反证读数在上表脚注里 —— 比留着差。
正本 §3.2 那份「五个补丁」的收编名单里,`tail-snap` 这一行照旧挂着。

### 9.4 门:这一单**没有**给几何门加断言,理由写在这儿

派工单要求「断言在现版 main 上必须先红」。做了两趟,**没做到**:

1. 几何门的 ② 本来就是这条判据(贴底跟随期间尾槽位移),但它在 `long` 那一档只读到
   **0.3px** —— 那一档 26 段 / 40 片 / 90ms,贴底跟随只剩一两秒,而抖 ② 是约两秒一个
   来回的慢摆,窗口正好接不住一个完整的来回;
2. 于是把 `long` 拉长到 96 段 / 64 片 / 110ms(探针那份长度,≈7 秒跟随)重跑:

两者唯一的结构差别是**这一轮离「刚打开这条会话」有多远**:探针把被量的那一轮发在

### 9.7 P1d:斜坡的产地查清了,**而且它推翻了 §9.2 的一半**(2026-09-21)

顺带证明了**它从来没被画出来过** —— §9.2 那张表里 main 那一行的 2.516px 是**探针

#### ① 斜坡是谁:`.rowLate` 的高度过渡(证据是它自己报的名)

诊断档(`--diag`)给采样器加了一句 `document.getAnimations()`(CSS 过渡也在里面),
斜坡那十几帧逐帧答的都是同一件东西:

```
article._row_ _rowLate_[height] , …[margin-top] , …[opacity] , span._seamLine_[composite+transform]
```

就是**上下文更新折痕那一行**(`ChatStream` 的 `contextSeamRow`,`.rowLate` =「事后
出现的行」,高度 / 行距 / 不透明度三量一起软着陆)。旁证两条,都对得上:
活消息行在**内容坐标**里的位置与列的分数高**逐帧同增**(1.86 → 1.66 → 1.42 → …
→ 0.06 → 0),也就是长出来的那一截**全在活消息行上面**;而那串增量是一条标准的
缓出曲线,不是台阶 —— 排除了候选 ①(跳渲的行补真高,那是台阶)。

一轮只有一条上下文更新折痕,所以**一轮只发生一次**。§9.2 里「约两秒一个来回」那句
话是我把「整轮 17 次变化 ÷ 8.2 秒」读成了频率,**是错的**:方向反转只有 1 次,
就是这一条斜坡的来回。

#### ② 它没有被画出来:rAF 读的是这一帧还没被 `stick()` 纠正的中间态

`requestAnimationFrame` 跑在「动画推进之后、**布局与 ResizeObserver 之前**」,而
`stick()` 住在产品那只 RO 的回调里。也就是说 rAF 读到的永远是**这一帧的半成品**:
过渡已经把列推高了,而纠正滚动位的那一句还没跑。

于是补了**第二份取样**:一只在产品那只之后注册的 `ResizeObserver`(RO 回调按注册
顺序跑,所以它读到的就是这一帧最后会被画出去的那份)。同一趟、同一份夹具:

| 取样口 | 尾槽 top 峰峰 | 取值集合 |
| --- | --- | --- |
| rAF(§9.2 用的那个) | 1.8–2.5px | 11–17 个 |
| **排在 `stick()` 之后(画出来的那一份)** | **0px** | **1 个(552.5 × 71)** |

**而且把 P1c 的 sticky 关掉重跑,画出来的那一份仍然是 0px / 1 个取值。**

推论要写清楚,不许含糊:**§9.3 那个 sticky 的裁决建立在一份被取样相位污染的读数上。**
它没有修好任何**画出来**的抖 —— 在这台机器、这份夹具、这个离屏档下,`stick()` 每一帧
都赢(诊断档数过:`scrollTop` 写入与 RO 回调都是**每帧恰好一次**)。sticky 今天的
真实价值只剩**结构性免疫**:尾槽的位置从此不再取决于「`stick()` 有没有在这一帧赢下
那场竞速」。那是一句值得留着的话,但它不是「修好了用户报的那个抖」。

#### ③ 那么真正被画出来的抖是什么:`tail-snap`,而且它一直在干活

同一份画出来的取样,把 09-15 的 `tail-snap` 拆掉(sticky 也一并关掉 = 回到 09-15
之前):

| | 画出来的峰峰 | 设备像素 | 反转 | 取值集合 |
| --- | --- | --- | --- | --- |
| 今天(`tail-snap` + sticky) | 0px | 0 | 0 | **1** |
| 只拆 sticky | 0px | 0 | 0 | **1** |
| **`tail-snap` 也拆掉** | **0.477px** | **0.95** | **39** | **46** |

所以这条链上**真正在治病的是 `tail-snap`**,一直都是;P1c 的 sticky 是它上面的一层
保险。正文那一块的**画出来的**亚像素相位只有 2 种(0.008 / 0.016,跨度 0.008px)——
也就是说**用户第二问「上面正在生成的内容也有抖动吗」,在这个harness 里答案是「没有」**;
§9.2 里那个「残值 56 个取值」同样是 rAF 相位的产物。

#### ④ 每帧在白做排版吗:不白做,但很贵

诊断档数出来:斜坡那一段里 `scrollTop` 写入与 RO 回调**都是每帧恰好一次**,没有
重复劳动。但代价是实打实的:`.rowLate` 那条高度过渡长在一条 **118,000px 高、400 行**
的列**靠近底部**的位置上,它每一帧改一次高度,就逼整条列重排一次,而 `stick()` +
`snapTail` 还要各读一次矩形。一条为了「软着陆」的 125ms 过渡,在真店规模上换来的是
十几帧的全列重排。

#### ⑤ 对 P2 锚定器的意思

三条,都是这一趟量出来的:

1. **锚定器不能建立在 rAF 读数上。** 任何「这一帧内容长了多少、该补多少」的计算,
   如果读在 rAF 里,读到的是半成品;要么住进 RO(与 `stick()` 同一相位),要么
   自己在 RO 里补一次。这一条对**门**同样成立 —— 见 §9.8。
2. **「把某一件钉住」的最省力形态是换坐标系,不是每帧算补偿。** sticky 那一版虽然
   没治好画出来的抖,但它把尾槽从「每帧算一次 nudge」里摘了出去,代价是零。P2 的
   锚定器凡是能用 sticky / 容器坐标表达的,就别用 `translate` 补偿。
3. **别在长列的底部做高度过渡。** `.rowLate` 那一手在小会话上是白送的,在 400 行上
   是每帧一次全列重排。P2 若要给「事后出现的行」软着陆,应当把过渡关进一个
   `contain: layout` 的盒子里,或者干脆只过渡 `opacity`。

### 9.8 P1d 的第二件(`gate:tail-jitter`)**没有做**,理由在这儿

派工单要求把探针原地升成门,并给两条反证:「拆掉 sticky → 必须红」「`bottom` 改回

能立的门**不是**派工单设想的那一条,而是:**贴底跟随期间,尾槽画出来的位置只许占

它守的是 09-15 的 `tail-snap`,反证真实存在。建不建、BUDGET 怎么写,等这一份读数
先被审过 —— 因为它同时意味着 **P1c 那一单要不要回滚是一个新的拍点**。

探针这一侧的改动已经留下(`scripts/probe-tail-jitter.mjs`):`--diag` 一档
(`scrollTop` setter 与 `ResizeObserver` 各包一层计数、`document.getAnimations()`

### 10.2 `gate:tail-jitter`(**绿了,已进 `verify`**)

而「画出来的那一份」只采到个位数,①② 永远卡在「采到 N 次 < 门槛」。这一单把它做绿了,
下面按「取样口怎么立住的 → 四个真因 → 今天的读数 → 反证」写。

#### ① 取样口换成「rAF 里排一个宏任务,在宏任务里读」

第一版的取样口是**在产品那只 `ResizeObserver` 之后再注册一只 RO**。它的毛病不是
注册顺序,是**它只在被观察的盒子尺寸变了的时候才响**:

- 位置还会被别的事改变(`scrollTop`、`translate`),尺寸没变它就不响;
- 它盯的是**节点**,React 一换列就哑;
- 真店档实测:整轮 **45 次**取样,贴底跟随那一段 **0 次**。

今天的口是一句话:**`requestAnimationFrame` 里 `postMessage` 出去的那个宏任务,跑在
这一帧的「更新渲染」(样式 → 布局 → 绘制 → 提交)全部走完之后、下一帧的任何东西
之前**,所以在那里读 `getBoundingClientRect()` / `scrollTop` 读到的就是**刚画出去的
那一份**。它每帧采一次,不挑帧、不认节点(缓存的几格一脱离文档就现找)。逼排版吗?
逼,但此刻布局是干净的——「更新渲染」刚走完、自那之后没有任何 JS 动过 DOM,所以
那一次 `getBoundingClientRect()` 命中缓存,不触发重排(09-10「探针自伤」判例要防的是
**在热路径上逼重算**,不是禁止读矩形)。

换口之后同一份夹具:真店档 **1653 次**取样(贴底跟随 1022 次),短会话档 **2181 次**
(贴底跟随 1519 次)。

#### ② 取样口凭什么算立住 —— 三条校准,都是真跑

| 校准 | 读数 |

两个字做墨迹加权质心):**纵向质心只有两个取值 212.6 ↔ 213.6,恰好差 1.00 视频像素
(= 1 设备像素),25 秒里跳 16 次**;横向质心峰峰 0.29px(不动)。另外那一行是
**右对齐**的,右缘恒在 x=416,而左缘在秒数从一位进到两位(9.9s → 10.0s)时从
x=201 跳到 187(14 视频像素 ≈ 7 CSS px)。

这一单把那两件都量到了:**横向那一件查清并修好**,**纵向那一件复现了、排掉了五条
候选、但没修好** —— 下面按「取样口 → 复现 → 反事实表 → 诊断 → 修了什么 → 门」写。

### 11.1 像素层取样口(新件 `scripts/lib/png-ink.mjs` + 门里的 ④ 段)

**为什么必须换一口**:`gate:tail-jitter` 到 P1f 为止读的是 `getBoundingClientRect()`
—— **盒的几何**。真机上那一格在贴底跟随的整段里恒为**一个取值 / 峰峰 0**,而录屏里
**画出去的字**在两态之间翻。盒不动、字在动,盒的读数就答不了这个问题。

新口两件家伙,都在 `scripts/lib/png-ink.mjs`(零依赖):

- `decodePng` —— `node:zlib` + 五种行过滤器,只解 CDP 吐的那一档(8 位、非隔行、
  colorType 0/2/4/6),其余当场抛错。**不为了读几百张小图把 `sharp` 拽进来**
  (它是原生的,而且是 `electron-builder.yml` 排除的那一族)。
- `inkCentroid` —— 灰度 → 减底色 → 小于阈值当没有 → 加权质心。与 Fable 量录屏那份
  脚本同源,三处收窄:**底色现算**(取这片区域的灰度众数,而不是写死 247,换主题
  照样成立)、**墨 = |灰度 − 底色|**(深字浅底与浅字深底同一条式子)、阈值 12。

门里的取样段三条纪律,每条都写在代码上:**裁框一次取定**(跟着元素走的裁框里质心
恒定,那是一只永远绿的门)、**量「停止」那颗钮而不是整行读数**(读数每 100ms 换字,
墨的分布本来就会变;停止钮的字形是常量)、**`captureBeyondViewport: false` +
`clip.scale: 1`**,图宽 ÷ 裁框 CSS 宽 = 一 CSS 像素几个图像像素(实测 2),读数一律
换算成设备像素。**它单独跑一段、打自己的记号 `phase='pixels'`** —— 一帧一次
`Page.captureScreenshot`(实测 ≈27ms / 36fps),混进 ①②③ 的窗口就是门自己造长帧。

**校准(这口凭什么算看得见)**:给**停止钮自己**加一格 `translate: 0 0.5px`
(dpr 2 上 = 1 个设备像素)再拍 —— 读出 **0.999 设备像素**,还原后读回 **0**。
挑停止钮而不是尾槽,是因为 `snapTail` 每一拍都重写尾槽那格 `translate`,往那儿写
校准量会被产品当场抹掉;停止钮这个元素产品从不碰。
(第一版把校准排在取样**之后**,那一段 14s 盖过了这一轮剩下的寿命,轮到校准时
run 已收场、裁框里一笔墨都没有,报了两个 `null` —— 已改成校准排在最前,取样循环
也改成「墨没了就收」。)

### 11.4 诊断:量到哪儿了,以及剩下的两条路

量出来的事实,按确定程度排:

1. **盒不动、字动 1 个设备像素**,两态、慢摆(平均每态停 ≈0.55s)。
2. **停止钮在尾槽里的行内偏移恒为 1.75 CSS px**(= 3.5 设备像素),整趟一个取值 ——
   所以**不是行内布局在动**。
3. 尾槽那格 `translate`(`snapTail` 写的)在两态里都**连续**变(−0.63 ~ −1.0 CSS px),
   两态的 `translate` 分布重叠 —— 所以**不是那一格翻**。
4. 滚动位的小数部分恒在 {0, 0.5} 之间(= 整数个设备像素);它的**奇偶**与两态有
   相关(41% vs 13%)但不是 1:1 —— 而那一格几何是**在截图之后**读的,差着几毫秒,
   这个相关本身还不足以下结论。

由 1–3 推出来的一句话:**这一行的字是在滚动内容层里按层内坐标栅格化的,而层内坐标
跟着列的分数高一直在走;`snapTail` 的 `translate` 纠正的是「盒在视口里的位置」,
它加在取整之后,所以纠正不了取整本身。** 这也正好解释 d/d2/g 为什么只平移不减少
翻动 —— 它们改的都是加在取整之后的那一项。

如果这句话成立,剩下的只有两条路,**两条都是拍点,不是顺手能改的**:

- **(i) 让这一行不住在滚动内容层里** —— 把尾槽的**内容**搬到滚动口之上的一层
  (绝对定位贴着滚动口底边),列里只留一格等高的空。它的层内坐标从此与列多高无关,
  栅格化不再重来。代价:①③⑧ 那几条几何判据、遮挡、输入框让位都要重新量,是一次
  结构改动。
- **(ii) 接受它,并把它变成一条**量得出来**的账** —— 这道门今天已经把读数打出来了
  (只报不判),下一次谁动这条链,读数会立刻告诉他变好还是变坏。

**这一单没有替用户拍这个板**(「行为裁定须先问」)。P1g 交的是:一口能看见它的
取样口、一张排掉五条候选的反事实表、以及上面这条诊断。

### 11.5 修了什么:读数行左对齐,左缘恒定

病根是 `TailSlot.module.css` 里 `.indicator` 那格 **`flex: 1`** —— 它进来时这一格
装的是 P1 那道**在扫的横线**(等待脸),`flex: 1` 说的是「横线把宽度吃满」。
P1b 裁定 B 把那道线删了,这一格只剩一枚 0.5em 宽的光标,而 `flex: 1` 留了下来:
它把读数与停止一起推到整行最右边,于是**「这一行有多宽」变成了「这一行从哪儿开始」**
—— 秒数一进位,左缘就往左跳 7 CSS px。

改法是**删掉那格化石**(`flex: none`),整行左对齐贴正文列左缘,顺序仍是
光标 → 读数 → 停止。`.readout` 本来就有 `tabular-nums`,所以数字进位也不抖;
秒数长一位只往右长。

**窄窗下不加 `overflow: hidden`,而且这一条是判词不是遗漏**:左对齐之后这一行的宽
= 光标 + 缝 + 读数的自然宽(1280 档实测那段字 91.25px,正文列 ≈720px),**它从来
撑不满**,挤压律一那条「结构行只截断不换行」在这一行上是空过的;而 `overflow: hidden`
会把停止钮的焦点环(画在盒外)剪掉 —— 为一个不存在的溢出付一个真的无障碍代价。

读数(整轮,跨过 10 秒那一下进位):

| | 读数行左缘峰峰 | 取值个数 | 这一轮跨到 |
| --- | --- | --- | --- |
| main(= 把 `flex: 1` 装回去) | **6.984px** | 2 | 17.97s |
| 这一版 · dev 短会话 | **0px** | **1** | 17.94s |
| 这一版 · dev 真店 | 0px | 1 | 11.96s |
| 这一版 · prod 短会话 | 0px | 1 | 17.98s |
| 这一版 · prod 真店 | 0px | 1 | 12.46s |

`stalled` / `stuck` 两档变长时同样只往右长 —— 它们是在**这一行的右端**接字
(`.readout` 是 flex,`stuck` 那半句是它后面多出来的一个孩子),左缘是第一个孩子的
左边,与后面接多少字无关;这一条由上面那张表的「1 个取值」覆盖(burst 那一档里
偶发的 1 秒停顿会把读数推进 `stalled`)。
