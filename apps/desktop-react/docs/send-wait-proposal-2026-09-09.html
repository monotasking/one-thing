发送 → 等待 → 回复 · 三台并排

每台底下都有输入框,自己发一条看。时间线按真机的量级模拟:账本收下 120ms,run/start 700ms,上下文更新再 250ms,首字再 1.4s。左台是现状照实重放,中、右两台是两种改法。

模拟条件:

现状

提案 A · 回复槽位同帧出

提案 B · 回合头折痕 推荐

现状:三段空档、一次顶开发送后只有气泡(半透明)。账本收下才变实。run/start 到了三点才出来 —— 这之前用户不知道它收没收到。上下文更新落账时整行插在气泡和三点之间,三点被往下顶一格。
A:按下即开槽,三点同帧发送那一帧同时画气泡和回复槽位,三点从第一帧就在。上下文更新落到槽位里面、三点上方,淡入;三点下移一行但那是「回复区在长」,不是「我的消息变了」。没有上下文更新时槽位就是三点,什么都不多。
B:回合头是一条折痕,等待就画在线上发送那一帧气泡下面开一条折痕:线上光束来回扫 = 在等;标签空着。上下文更新落账时标签淡入「上下文更新 · 变量 2」,不占新行。首字到,光扫停、线变实、正文在线下开始。没有上下文更新时标签一直空,线在首字后淡出,正文往上补 1px 都不动(线的高度不算进正文)。同一条线三段话:在等 → 补了什么 → 从这儿开始回。

与压缩折痕同一族(线 + 居中标签,光扫 = 进行中),读数环照旧压缩时脉动、每轮滑到新值。B 里三点整个不要了 —— 一个回合只有一种「进行中」的动作:线上的光。
