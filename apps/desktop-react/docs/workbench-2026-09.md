## 0. 需求归纳与现状诊断

用户 09-04 口述,归纳成六条:

1. Dock 上那块叫「Viewer」的瓦没有必要:平时不该显示,它只在打开文件时才有意义。
2. 查看器要升级成**文件标签**:一个文件一个 tab,tab 的名字就是文件名;tab 里面不再画文件名和关闭按钮,
   因为「宿主窗口的关闭」与「里面那个关闭」现在是两个不同的东西,有误导。
3. tab 可以打开多个;关掉一个 tab 的时候,可以选择**隐藏**(还在,只是不显示)或**关闭**(没了)。
4. Sessions、Projects、Files 里的条目要能**拖**到中央区域,或者拖到四条边的区域里。
5. 中央区域(现在的聊天区)要能展示更多东西,不只是聊天。
6. 现在那个「全屏」不是全屏:它只盖住聊天那一栏。要的是**整扇窗口的全部 UI 都被盖掉**的全屏。

追加的聊天报障两条:

7. 我贴在底部发消息时,**必须能看见自己刚发的那条**;现在有时看得见有时看不见。
8. 流式回复的**自动跟随**做不到;而且跟随只该在贴底(或某些明确场景)时发生;
   我在上面浏览旧回复时发消息,**不要**把我滚到底部。

追加的工具调用报障三条:

9. 工具调用流式期间**完全看不到它做了多少**,只看得到「正在流」,感觉很差。
10. 连续相同的工具调用会成一「组」,组上挂着一句注释样的东西,看起来很怪。
11. 「组」的 UI 与「单个工具调用」的 UI **不匹配**,让人困惑。

用户明确要求:所有这些要**整体**考虑、分析、设计,一次交齐,再由用户点名调整。

## 1. 模型:内容 / 树 / 区域三层正交,加两个瞬态

一句话:**屏幕上任何一块能看的东西都是一个「内容引用」;内容引用住在某棵「拼贴树」的叶子里;
每棵树归一个「区域」持有。**「全屏」和「舞台」是两个独占的瞬态,不是区域。

### 1.1 内容引用与内容种类(什么)

```ts
/** 一块内容的身份。kind 是种类名,key 是这一种里的哪一个。核心层只认这两个字符串。 */
export interface ContentRef {
  kind: string   // 'panel' | 'file' | 'session' | 'files-root' | …(核心层不枚举)
  key: string    // panel → 瓦 id;file → 绝对路径;session → 会话 id;files-root → 目录路径
}
export const refId = (r: ContentRef): string => `${r.kind}:${r.key}`

/** 一种内容的自述。每一种在自己的模块里 register 一次,核心层只读表。 */
export interface ContentKind {
  id: string
  /** 单例种类(今天的 12 块瓦):同一个 key 全应用只许一个实例;file/session 不是。 */
  singleton: boolean
  /** 身份由内容自答:文件名 + 未保存丸 + 全路径提示。走既有 stage/live-title。 */
  title(ref: ContentRef): LiveTitle
  icon(ref: ContentRef): LucideIcon
  render(ref: ContentRef, visibility: PanelVisibility): ReactNode
  /** 关闭前的一问(脏文件确认)。缺席 = 直接关。 */
  beforeClose?(ref: ContentRef): Promise<'close' | 'cancel'>
  /** 实例被真正丢弃(关闭,不是隐藏)时清它自己的状态。 */
  dispose?(ref: ContentRef): void
  /** 这一种可以开在哪些区域。缺席 = 都可以。今天只有 chat 在 T4 之前限定 center。 */
  regions?: RegionId[]
}
export function registerContentKind(kind: ContentKind): () => void
```

`ContentKindRegistry` 是 `content/index.tsx` 那张 `RENDERERS` 表的升级:今天的 12 块瓦整体登记为
`panel` 这一种(`key` = 瓦 id,`singleton: true`);文件登记为 `file`(`key` = 路径,标题 = 文件名,
`beforeClose` = 现有 `ViewerCloseConfirm` 那一问);T4 的会话登记为 `session`;项目拖进区域时登记为
`files-root`(以那个目录为根的文件树,`key` = 目录路径)。**查看器从「一块瓦」降格为「一种内容」**,
`VIEWER_ITEM_ID` 那一行从 `STAGE_ITEMS` 删掉。

`data/viewer-source.ts` 从单例改成**按路径各持一份**:`instances: Record<path, ViewerInstance>`,
`ViewerInstance` 就是今天 `ViewerSourceState` 里 `file / pending / view / edit / scrollTop` 那几格。
`useViewerInstance(path)` 是读口,`FileViewer` 收 `path` 而不是读全局。隐藏的 tab 实例留着,
关闭的实例 `dispose`。

### 1.2 拼贴树(区域内部怎么摆)

```ts
export type PaneNode =
  | { kind: 'leaf'; id: string; tabs: ContentRef[]; active: number; preview: string | null }
  | { kind: 'split'; id: string; dir: 'row' | 'col'; ratio: number; a: PaneNode; b: PaneNode }

/** 树里的一个位置:哪个区域、哪片叶、第几个 tab。隐藏与全屏都靠它记「回哪儿」。 */
export interface PaneLocation { region: RegionId; leafId: string; index: number }
```

叶 = 一组 tab(单 tab 时不画 tab 条,就是今天的形);`preview` 记的是这片叶里「预览 tab」的
`refId`(§2.1)。分隔杆消费既有 `ui/Splitter`。树的操作词汇是封闭的一组纯函数,全部住在
`workbench/tree.ts`:`insertTab` / `removeTab` / `moveTab` / `splitLeaf` / `activate` /
`prune`(空叶剪掉、split 只剩一支就提升)。**核心层不出现任何内容种类的名字**。

### 1.3 区域(树归谁)与两个瞬态

```ts
export type RegionId = 'center' | `edge:${ShelfSide}` | `float:${string}`

export interface WorkbenchState {
  /** 每个区域一棵树。center 永远在;某条边没东西时没有那一格;浮窗按 id。 */
  regions: Partial<Record<RegionId, PaneNode>> & { center: PaneNode }
  /** 架子与浮窗的**外壳**几何,原样继承今天的 shelves / floats / floatOrder。 */
  shelves: Record<ShelfSide, { thickness: number; collapsed: boolean }>
  floats: Record<string, FloatRect>
  floatOrder: string[]
  /** 打开着但不显示的内容,记着它该回哪儿。 */
  hidden: Array<{ ref: ContentRef; returnTo: PaneLocation }>
  /** 两个独占瞬态:舞台(原样)与全屏(§4)。 */
  stage: ContentRef | null
  full: { ref: ContentRef; from: PaneLocation | null } | null
  /** 位置记忆,键从瓦 id 换成 refId,形状不变。 */
  memory: Record<string, PlacementMemory>
}
```

与今天 `StageState` 的对应关系:`placements: Record<id, Placement>` 变成**派生值**
(一个 ref 在哪棵树里,它的落点就是那个区域;哪棵树都不在、也不在 hidden 里 = 收在 Dock);
`ShelfState.tabs: string[]` 变成 `regions['edge:right']` 这棵单叶树;浮窗从「一块瓦」变成
「一个装着树的区域」,于是浮窗里也能并 tab、也能分屏。**形态机的全部纯函数(吸边、撕出、
钳制、Dock 唤醒、退层链)一个字不动**,它们管的本来就是区域的外壳。

### 2.1 打开

文件树单击一行 = 打开。落在哪儿由「默认落点」决定(今天的七档「打开方式」改名为「新标签开在哪」:
面板内 / 中央区 / 浮窗 / 四条边;语义从「把那块瓦摆到哪」变成「把这个 ref 插进哪个区域的活动叶」)。
**面板内**保留:它是 `FilesPanel` 自己那条分栏,不进树,语义不变。

**一扇新窗开在哪**(W7-p 裁定 5 + 修一轮裁定 1,审计 A 的 A6;正本以本段为准):
身量 **640×480**(08-31 那次为模型服务那块两栏面加宽到 880 的账被推翻 —— 拿最宽那块面的
需求去定全体默认值,代价是每扇窗一开就吃掉大半个屏;那块面的挤由它自述最小身量来治,
形态机今天还没有那一口,记在 `transitions.FLOAT_DEFAULT_W` 的判词里),位置锚在**中央区**
(四条架子与顶栏切完剩下的那块地)**右上角内缩 24px**,已有 n 扇未关的窗时整体往左下层叠
n×28,挪出中央区就回绕到起点。

从前是**恒定居中**:那个矩形正压着聊天区正中与输入框,而且连开四扇一模一样地叠在一起。
**产地只有一个**(`transitions.freshFloatRect`)—— 这是修一轮补的那一半:裁定 5 落地时锚与层叠
只接在右键菜单那条路上,而最常走的点瓦 / 快捷键那条走的是召唤第一态「开」,它由
`completeMemory` 当场造一个恒定矩形塞进「记忆」里,`placeAs` 于是看到「已经有矩形了」直接
跳过产地。今天 `PlacementMemory` 的 float 那一档 `rect` 是**可选的**:记忆里没有矩形就是没有,
缺矩形一律落到那只产地。

**预览 tab**(拍点 ①):浏览一棵树时单击十个文件不该留下十个 tab。推荐 VS Code 的做法 ——
单击开出来的是**预览 tab**(名字斜体,一片叶里至多一个),下一次单击**替换**它;以下动作把它
转成固定 tab:树行 ↵(本台「↵ = 确认」的既有语义,`FILES_KEYS` 里 `⌘↵` 是详情、`↵` 是进查看器)、
开始编辑、拖动它、右键菜单「保留」。本台禁双击,所以 VS Code 的「双击固定」那一格由 ↵ 顶上。

### 2.2 一格一檐(解决两个 ✕)

规则只有一条:**一片叶只有一条檐,那条檐就是 tab 条;内容自己不画檐。** 于是:

- 面板内 / 架子 / 中央区:叶的 tab 条是唯一的檐。单 tab 时 tab 条退化成一条身份带(图标 + 名 +
  未保存丸),右端是这片叶的动作组(分屏 ▸ / 全屏 / 隐藏的标签 ⋯)。
- 浮窗:浮窗的标题栏**就是**它里面那棵树根叶的 tab 条(与浏览器一致:tab 长在窗口檐上)。
  浮窗那颗 ✕ 从此只有一个意思:关这扇窗(= 把里面的 tab 全部**隐藏**,不是关闭 —— 窗子没了,
  内容还在 hidden 里,这与今天「收回 Dock 不丢状态」同一条判据)。
- 舞台 / 全屏:宿主檐上只有这块内容的身份与退出;tab 的 ✕ 不在那里画。

`ViewerChrome.tsx` 整件退役;`HOST_OWNS_CHROME` 那张表随之消失 —— 它本来就是「谁画檐」这个
问题没有唯一答案时的补丁。~~文件类型工具条(markdown 的渲染 ⇄ 源码)搬到叶檐的动作组里,
由 `ContentKind` 以 `toolbar?(ref)` 自述。~~ **(W7-c 裁定 2 顶掉:顶栏右端只留 ⋯ 与 AgentChip,
`ContentKind.toolbar` 整格退役;那两档看法搬进内容区自己的右键菜单,由查看器型自述
`ViewerHandler.viewModes` 那组纯数据 —— 动作单产地是右键菜单,檐上不再有第二个入口。)**

### 2.3 隐藏与关闭是两个动作

### 2.4 激活与移动

激活 = 点 tab / 叶内 `⌃Tab` 轮转;移动 = 拖(§3)或右键「移到 ▸ 中央 / 左 / 右 / 上 / 下 / 浮窗」。

### 3.1 拖什么、落到哪

| 拖的来源 | 变成的 ref | 备注 |
| --- | --- | --- |
| 文件树一行 | `file:<path>`(目录 → `files-root:<path>`) | 已打开的文件拖 = 移动那个 tab,不复制 |
| 会话总览一行 | `session:<id>` | T4 之前:落到中央 = 切换当前会话;落到别处 = 结构化拒绝(浮影变灰,说「会话多开在下一期」) |
| 项目一行 | `files-root:<path>` | 以项目目录为根的文件树 |
| 一个 tab / 单 tab 叶的身份带 | 它自己 | 拖出所有区域 = 撕成浮窗(既有 `shouldTearOff`) |
| Dock 上一块瓦 | `panel:<id>` | W4 之后与文件走同一条路;之前照旧 |

**落点表(W3-b 改甲;次序即语义,从上往下问)**:

| 落点 | 判据 | 结果 | 屏幕上的预示 |
| --- | --- | --- | --- |
| **某条标签条** | 条的矩形,上下各外扩 `TEAR_OFF_DISTANCE` 24 | 插到第 `at` 格(同叶 = 换序,异叶 = 搬过去) | **那条条腾出一个空位**(`.ph`),不画高亮 |
| 窗口四条**边带** | `SNAP_BAND` 24px(既有 `snapSideAt`) | 进那条边的架子;架子空着就新建单叶树 | 薄膜 + 一圈实线 + 一句话(`film`) |
| 某片叶的**四条边带** | 离那条边 < `DROP_EDGE_PX` **16px** | 按向切分:新叶放那一侧,比例 0.5 | 那条边上一根 **4px** accent 杠(`bar`) |
| 某片叶的**叶身** | 其余全是(线上算叶身) | 并入这片叶,成为活动 tab | 叶内一圈 `--accent-ring` 细环(`ring`),**不铺色块、不写字** |
| 什么都没碰到 | —— | 撕成浮窗(既有 `floatRectForGrab`) | 一圈虚线轮廓(`outline`) |
| 这次拖拽不收 | 来源自述的 `accepts` | 空动作 | 浮影变灰 + 一句理由,不画高亮 |

W3 那时是反过来的:中心区**内缩 25%**、其余全是分屏 —— 一片叶上一多半面积会切一刀。
甲把它倒过来,误分屏从「一多半概率」变成「必须故意去够那条边」;而分屏本来就是低频动作。

判据全部是纯函数 `workbench/drop.ts` 的 `dropTargetAt(pointer, geometry)`,
`geometry` 由宿主量一次叶矩形与**条矩形**递进去。返回:

```ts
export type DropTarget =
  | { kind: 'leaf'; region: RegionId; leafId: string; zone: 'center' | 'n' | 's' | 'e' | 'w' }
  | { kind: 'strip'; leafId: string; at: number }   // W3-b
  | { kind: 'edge'; side: ShelfSide }
  | { kind: 'float' }
  | { kind: 'refuse'; reasonKey: MessageKey }
```

落区高亮是一层 `DropOverlay`(消费 `ui/float` 的定位原语,不手写),四种画法由
`DropFeedback.shape` 说(`film` / `ring` / `bar` / `outline`)。**叶内不再铺半透明色块、
不再写字** —— 那句话盖在正在读的内容上,而环与杠自己已经说清了「并入」还是「往哪边切」。

**一次手势,两种模式,一条 `DragSession`**(W3-b 裁定 4/5):

- **换序模式** —— 指针在**本条的带内**。那一格 tab 自己抬起横向跟手(`data-lift`,
  `transition: none`)、邻居用 `transform` 让位(`data-shift`,**一帧不经过 React**,
  与 Splitter 的 liveVar 同一条纪律),**浮影一个节点都不画**;松手 = 一次同叶
  `reorderTab` + 播报。
- **撕下模式** —— 指针离开带 > 24px。抬起收掉,那一格在原位**折成 0 宽**(`data-torn`,
  邻居合拢,元素不卸载、body keep-alive 不动),浮影换成**一张 tab 形卡片**
  (图标 + 名、36px、圆角、阴影、轻微倾斜;W3 那枚 28px 芯片退役 —— **一枚浮影一种形**,
  文件行 / 会话行 / Dock 瓦也用卡片);回到**任何一条**标签条的带里,那条条腾出空位。
- 模式由 `DragSession` 那一格**「带」**(`band?()` + `bandSlack`)每帧报回来
  (`inside | outside` + 从 inside 出来的那一帧),消费方只是它的读者 —— 第二条会话会在
  Esc / pointercancel / 窗口失焦三条路上各漏一次归零。
- **Esc 取消**:折的展回、让位清零、空位收掉、卡片消失,**树逐字不变**。

拖拽起手时,**被拖的行不离开列表**(树 / 面常驻铁律),只在浮影上动;被拖的 tab 也
**全程是同一个 DOM 节点**(抬起 / 撕下 / 落回都不重挂)。

**键盘等价**(裁定 9 的第四组):叶檐菜单里的「左移 / 右移」与拖着换序走的是**同一只**
`reorderTab(leafId, from, at)`,播报也在那一只里 —— 播报是落定的一部分,不是菜单的装饰。

## 4. 真全屏

### 4.1 定义

`full: { ref, from }` 是一个独占瞬态:**这一块内容铺满整扇窗口,顶栏、四条架子、所有浮窗、Dock
全部不可见**。它不是新的 Placement kind,是「把某一片叶的活动 tab 投影到一层」—— 退出时内容回到
`from` 那个位置(树没动过,所以「回去」是零成本的)。

| | 舞台 stage | 盖 cover(**W2 已退役**) | 全屏 full(本稿) |
| --- | --- | --- | --- |
| 盖顶栏 | 否 | 否(让出 `--topbar-h`) | **是**(只留一条 28px 檐带,见 4.3) |
| 盖架子 | 是(scrim 罩住) | 是 | 是 |
| 盖浮窗 | 否(200 > 舞台) | 否(100 < 200) | **是** |
| 盖 Dock | 否 | 否 | **是**(Dock 转「自动隐藏」,贴边停留仍唤得出) |
| 退出 | Esc / ✕ / 收回 | Esc / ✕ / 点底 | Esc / 檐带 ✕ / 同一个快捷键再按一次 |

**盖并入全屏**(拍点 ②;**W2 已落地**):`cover` 这一档整套退役 —— `Placement` 联合里没有它了,
`OPEN_PLACEMENT_CHOICES` 第三行从「盖满」改成「全屏」,「所有应用」的 `defaultPlacement` 是
`{ kind: 'full' }`,存量记忆里的 `cover` 由 stage persist **v10** 映射成 full(扁平层与
`byWorkspace` 每个空间那一格两条路都走)。全屏**不是**一种 Placement:它是拼贴台那本账上的一格
瞬态(`workbench.full`),树一个字不动 —— 所以 `PlacementMemory` 里有 `full`,`Placement` 里没有。

> **W7-p 推翻了这一段的两处**(裁定 2,审计 A 的 A2;正本以本框为准):
>
> ① **进全屏不写记忆。** W2 落地时这一支照「上舞台」的样子写了三步(摘树 →
> `remember(id, { kind: 'full' })` → 说给 store 听),前两步都是错的,而且是同一个错的两半:
> 全屏被当成了一种住处。真机后果两条,都致命——一块钉在右边的瓦全屏一次,记忆被改写成
> `full`,退出后它回了 Dock,此后**点它永远进全屏**,右架子再也回不来(用户没有任何一步能
> 撤销它);而「摘树」让只剩它一格的那条架子当场整条消失。
> 今天 `placeAs` 的 full 支只剩一句「把谁去铺说给 store 听」,一格状态都不写。
>
> ② **退出回原住处,而「回」不需要动作。** 全屏**不摘树**,所以那一格 tab 全程住在它原来
> 那片叶里;`store.land` 落地时**不递 `from`**,让拼贴台自己问树 —— 它此刻在哪一格,退出就
> 露出哪一格。哪棵树都不在的(出厂即全屏的「所有应用」)问出来是 `null`,退出即回 Dock,
> 与 W2 逐字相同的行为,只是不再靠主动摘一次树来制造那个 `null`。
> `PlacementMemory` 里 `full` 那一档因此只服务**出厂档**(`items.defaultPlacement`),
> 不再由任何手势写进去。
>
> ③ **全屏期间召唤别的瓦 = 先退全屏再召唤**(A9)。否则那块面开在全屏层**底下**,
> 屏幕上什么都没变、焦点也没进去 —— 用户按了一下,得到的是「没反应」。

### 4.2 层序与 Dock

`--z-full` 取 **550**:高于浮窗(200)与 overlay(500),低于 modal(600)—— 全屏里弹出的确认框、
菜单(680)、Tooltip(700)、Toast(800)照常在上面。Dock(650)**不靠 z 序压**,靠状态:进入全屏时
`dockDisplay` 视作 `autohide`(不改用户档,只在 full 期间生效),沿用 `shouldShowDock` 的唤醒 / 留驻
两个语义,贴边停留 `DOCK_WAKE_DWELL_MS` 唤出;退出全屏恢复用户档。架子与浮窗**不卸载**,只是被
这一层盖住(它们的 `FocusScope` 在 full 期间标 `inert`,路径截断,键盘不会漏进看不见的面)。

### 4.3 顶栏与红绿灯

窗内全屏时 macOS 的三颗红绿灯仍在窗口左上角。全屏层顶上留一条 **28px 檐带**(`--full-strip-h`):
左边让位给灯,中间是这块内容的身份(图标 + 名 + 未保存丸,`HostTitle`),右端一颗「退出全屏」。

让位读的是**与 `TopBar` 同一个 `--topbar-lead`** —— W2 把那个变量的三档定义从 `.bar` 提到了
**壳根**(`AppShell.module.css` 的 `.shell`),判据(有没有灯 / 是不是系统全屏)由 `AppShell` 问一次、
写成壳根上两格 data 属性,两条带子只消费。于是两条带子的左缘永远逐像素对齐(`gate:squeeze` 的
`[10c/11]` 量的就是这一句),而「让位」这件事只有一个产地。**系统全屏那一档收到 `--sp-4` 而不是 0**
——初稿写「归 0」,按代码事实改口:0 会让内容贴死窗口左缘;「这台机器上根本没有灯」
(Windows / Linux / 浏览器壳)那一档才是 0。

檐带**常驻,不自动收起**(样例 B 那种「指针离开顶部 2s 后收成 4px 把手」的做法 W2 不做,留账)。

### 4.6 与拖拽(W3)的接缝:两条,方向相反

W2 与 W3 各自成批、互不知道对方,合树时这两台机器在**同一棵树**上相遇。裁定两条,
它们是同一句话的两半 ——「全屏层盖着整棵树的时候,拖拽说的话与用户看见的东西不许分家」:

- **a. 全屏期间一下都不许起拖。** 落点判据吃的是起拖那一刻量的**底下那棵树**的几何
  (`measureDropGeometry`),而此刻那棵树被全屏层盖着、每一片叶都带 `inert`、顶栏与四条
  架子全在层底下;FullLayer 自己的檐带上也没有任何一件是可拖的。真让它起拖,高亮就画在
  一块用户根本看不见的矩形上。落点是 `useContentDrag` 的 `onStart`(五种来源共用的那一只,
  `useTabDrag` 经它转手,所以**产地一处**),判法与「`ref()` 答 null」逐字同一条:整场
  不成立,不是中途取消。
- **b. 落定之前先把全屏收掉。** 落定会改树(并入 / 切一刀 / 撕一扇窗),而改完之后用户
  看见的还是那块铺满的面 —— 那是「按了没反应」;`land()` 的焦点还会送进一片 `inert` 的叶
  里。所以 `drop-commit.dropRef` 在 `refuse` 那一句之后先收全屏(被拒绝的那一下什么都
  没发生,不该顺手改形态)。它**不问是哪一块**在全屏:任何一块盖着,树都看不见。

**「收全屏」这个动作只此一份**:`workbench/store.exitFullIfOpen()`,答「刚才真收了没有」。
三处调它 —— Dock 上再点一下那块正铺满的瓦(`stage/store.clickDockIcon`)、召唤四态的第四格
(`summonItem`)、拖拽落定(`dropRef`)。前两处先问「是不是这一块」再收(那是 toggle),
第三处不问。守卫在 `workbench/__tests__/full-drag-seam.test.tsx`(四条,断言的是结果不是
调用),真机门不加场景 —— gate:drag 的七个场景全在全屏关着时跑,那正是它该守的常态。

## 5. 聊天跟随

### 5.1 一个状态机,两个态

```ts
export type FollowMode = 'pinned' | 'browsing'
export interface FollowState {
  mode: FollowMode
  /** 浏览中时下面长出了没看见的东西(流式增量或自己刚发的那条)。 */
  unseen: 'none' | 'sent' | 'reply'
}
```

`pinned` = 贴底,内容长高我就跟;`browsing` = 人在看上面的东西,我不动。
**判据只有位置与意图,没有计时器、没有「这一下是我自己滚的」标志位**(沿用 `useEnterAtBottom`
的那条纪律:自己落的那几下正好在底,人往上翻才会离底)。

| 信号 | 从 | 到 | 说明 |
| --- | --- | --- | --- |
| 进入会话(既有进场落底) | — | pinned | `useEnterAtBottom` 并入本状态机,成为「进场 = pinned」这一格;它盯高度变化的 ResizeObserver 就是流式跟随要用的同一只 |
| 用户滚动离底(`gap > AT_BOTTOM_EPS`,来源是 wheel / 触控板 / 键盘 / 拖滚动条 / TOC 跳转) | pinned | browsing | 与今天出口一同一条判据 |
| 用户滚回底(`gap ≤ AT_BOTTOM_EPS`) | browsing | pinned,`unseen = none` | 人自己回来了就接着跟 |
| 内容长高(流式 delta / 异步高亮 / 图) | pinned | pinned,`scrollTop = scrollHeight`(layout 相位,首帧就在底) | 这就是「自动跟随」 |
| 内容长高 | browsing | browsing,`unseen = reply` | **不滚**,只亮丸 |
| 发送 | pinned | pinned,自己那条落到视口里 | 需求 7 |
| 发送 | browsing | browsing,`unseen = sent` | 需求 8:不滚,丸说「已发送」 |
| 点丸 / `End` / TOC 点最后一轮 | browsing | pinned,滚到底 | 明确场景下的跟随 |

### 5.2 发送后自己那条落在哪(拍点 ⑤)

两种做法都能满足「看得见」:**落底**(自己的消息贴在输入框上方,回复从下面长出来、把它往上推)与
**置顶**(ChatGPT / Claude 的 hold-top:自己的消息滚到视口顶部,下面留白等回复,阅读位置整段不动)。
推荐**落底 + 跟随**:它与用户口述的模型(「贴底就跟」)是同一件事,零新概念;置顶留作后续可选档。

### 5.3 「回到最新」丸:生成中是三个点

浏览中且 `unseen ≠ none` 时,聊天区**底部居中、输入框上方**浮一枚丸。它有三种脸(09-04 用户定:
生成中不要「有新回复」那句字,要**三个点带动画**):

| 此刻 | 丸上画的 | 无障碍名 |
| --- | --- | --- |
| 回复正在流(`streaming`) | **三个点**,依次起伏(`--kf-dots`,动效档 none = 三个静止的点) | 「正在生成,回到最新」 |
| 自己发了一条,回复还没开始 | `↓ 已发送` | 同文案 |
| 流已收场,下面还有没看的 | `↓ 回到最新` | 同文案 |

点它 = 滚到底 + pinned。它是聊天区自己的一个块,不是 Toast、不是通知(零 Toast 的禁令照守);
消费 `ui/Button`(pill 形)+ `announce()` 播报一次;`aria-live` 不加在丸上(流式每帧一句会念疯)。
pinned 时丸不画。滚动条不做「到底」指示,丸就是唯一的指示。

同一枚**三个点**还有第二个落点(拍点 ⑫,推荐做):回复槽位刚开出来、第一个字还没到的那段空档
(thinking 与网络往返),助手气泡里画同一组点;第一个 delta 到达即换成正文与尾部光标。
今天那段空档是一片空白,与「不知道它是不是卡住了」同源。

### 5.4 与 TOC、与 scroll anchoring 的关系

TOC 的 `pickTurn` 是 smooth 滚到某一轮 → 它必然离底 → browsing,不需要特判;点最后一轮时
`gap ≤ EPS` 自然回 pinned。CSS `overflow-anchor` 保持默认 `auto`:browsing 时它把阅读位置钉在
可见元素上(上面的异步高亮长高不会踹人),pinned 时我们显式赋 `scrollTop`,两者不打架
(赋值发生在 layout 相位,浏览器的锚定在其后的滚动步里看到的已经是底)。

### 5.5 落点与门

`content/ChatStream.tsx` 的 `useEnterAtBottom` 改名 `useFollowBottom`,状态机纯函数在
`content/follow.ts`(输入:mode / gap / 事件种类,输出:下一个 state + 要不要赋 scrollTop),
jsdom 单测钉八条转移;真机门 `gate:chat-follow`(CDP 起离屏窗,伪 provider 流式 200 段:
贴底 → 每帧在底;wheel 上翻 → 不再动、丸亮;发送两态各一次)。

### 5.6 输入框是一块悬浮的玻璃,不是一行(09-04 用户追加)

用户原话:输入框现在和聊天是上下完全分开的;要它是一个**独立的块**,不影响聊天内容,输入框短的时候
能**透过它看到下面的文字**;模型选择、命令、@ 文件那些面板也要跟着调。

今天:`AppShell` 的 `.center` 是一列 flex,`.chatArea`(消息流 + TOC 键列)在上、`<Composer/>`
在下,各占一段高度 —— 消息流的滚动容器到输入框上缘就结束了,文字永远不可能在输入框底下。

本稿:

- **输入框绝对定位在 `.center` 的底部**,居中、宽度仍是 `--pr-col`;消息流的滚动容器**铺满整个
  `.center`**,底部内边距 = 输入框实高 + **一段充足的气口**(`--composer-h` 由输入框上的 ResizeObserver
  写进 CSS 变量,输入框长高、抽屉开合都跟着变;`scroll-padding-bottom` 同值,TOC 跳转与 scrollIntoView
  才不会把目标滚到玻璃底下)。于是贴底时最后一条消息稳稳停在输入框上方,往上翻时正文从玻璃底下流过。
- **气口要充足,不许贴着**(09-04 用户追加:「正文内容距离输入框要有一点距离,要留有充足的空间」):
  气口是一个 token `--composer-gap`,推荐 **40px**(与消息之间的物件档间距 `--pr-obj` 同量级,
  约两行正文的高度),不是今天那种一格 `--sp-3` 的紧贴。贴底时最后一条消息的下缘到玻璃上缘至少这么多;
  跟随丸就落在这段气口里(丸的 `bottom` = `--composer-h` + 气口的一半),贴底时气口是空的,丸不会盖住字。
  这个数进 `gate:chat-follow` 的断言(「贴底时最后一条的下缘 ≤ 玻璃上缘 − `--composer-gap`」)。
- **玻璃**:底 `--glass` + `backdrop-filter: blur() saturate()`(磨砂),边线降一档透明度,阴影 `--sh-2`。
  磨砂还是清玻璃是拍点 ⑪:清玻璃底下的正文是可读的,会和正在打的字打架;磨砂只剩形与色,
  「有东西在下面」这件事仍然看得见。推荐磨砂。
- **抽屉开着时整块转不透明**(`--surface-2`):命令 / @ 文件 / 模型三张清单是要读的,不能叠在
  正文上;关掉抽屉回玻璃。抽屉照旧在输入框**里面**往上长(它本来就在块内,块浮起来它跟着浮),
  高度上限从今天的固定值改成 `min(既有上限, .center 高度的 40%)`,正文永远露出上半截;
  清单的最大高度约束与选中项 scrollIntoView 不变(既有法条)。生成读数那张 `MeterCard` 与
  `AskForm` 同在块内,一起浮。
- **不改的**:输入框仍在 `.center` 的 DOM 里(错误边界、响应链作用域、`useFloatDismiss` 的点外关
  一字不动);Dock 停靠底边时的让位 `--dock-reserve-h` 改加在输入框的 `bottom` 上(绝对定位不吃
  父级的内边距);拖文件进输入框的 `.dragging` 态不变;跟随丸的 `bottom` 改成 `--composer-h` + 气口。
- 门:`gate:squeeze` 加一屏(抽屉全开 + 输入框长到上限时正文仍露出 ≥ 60%);`gate:chat-follow`
  加断言「贴底时最后一条消息的下缘在输入框上缘之上」。

### 5.7 读数的进位:数量 k / M,时间只到 0.1s(09-05 用户追加)

今天有**两个产地**在各写各的:`composer/transitions.ts` 的 `formatCount`(小写 k,没有 M,一百万写成
`1000k`)与 `providers/projection.ts` 的 `formatTokens`(大写 K,有 M,不带小数)—— 同一个数在输入框
读数里和模型目录里长得不一样。时间那边 `content/tools/status.ts` 的 `formatDuration` 一秒以下写毫秒
(`339ms`),一秒以上一位小数(`1.2s`),两种单位在同一张卡上换来换去;`StreamReadout` 又是整秒。

本稿收成**一个产地** `apps/desktop-react/src/format/quantity.ts`,两个函数,两处旧产地退役:

```ts
/** 数量:999 → '999';1 200 → '1.2k';200 000 → '200k';999 950 → '1M';1 250 000 → '1.3M';128 000 000 → '128M'。
 *  小写 k、大写 M;一位小数,整数不留 .0;先四舍五入再判档,所以 999.95k 会进到 1M 而不是 '1000k'。 */
export function formatQuantity(n: number): string
/** 时间:只到 0.1s,永不写毫秒。0.3s / 12.4s;≥ 60s 换成 '1m 05s'(分钟档不再带小数)。 */
export function formatDuration(ms: number): string
```

用它的地方:输入框读数卡(上下文 / tokens)、模型目录与选择器里的窗口大小、工具卡的耗时与头行总耗时、
消息尾的生成读数(改成一位小数,与 10Hz 的读数节拍正好同一精度)、用量面板。单测是一张表
(数字 → 字符串),边界各钉一行(999 / 1000 / 999 950 / 1 000 000 / 59 950ms / 60 000ms)。

### 5.8 模型选择器带上思考等级(09-05 用户追加,三个方向在比稿页)

## 6. 工具卡:一种卡、三段流中态

### 6.1 一件事一张脸

**工具卡 = 一张卡装一列「步」**。一次调用是一步的卡,连续多次调用是多步的卡;两者是同一个组件、
同一张壳(今天 `.toolCard` 那张:1px `--line-1` 边、`--r-2`、`--surface-2`、`--sh-1`),
**没有第二种画法**。今天的 `ToolGroup` 与 `ToolRow` 合成一个 `ToolCard`,`GroupedNode` 里
`tool-group` 这一格原样保留(它本来就是「一次也是一组」)。

```ts
export interface ToolCardModel {
  steps: ToolStepModel[]           // 时间序,不重排(失败不置顶,拍点 ⑨)
  /** 多步时的头行:由各步的 name 拼成「rg · read ×3 · edit ChatStream.tsx」,不再是计数句。 */
  head?: { icons: string[]; text: string; failed: number; durationMs?: number; live: boolean }
}
```

- **一步**:卡里只有那一行(与今天单发逐像素相同)。
- **多步,收起**:卡里是**头行**(与步行同一套栅格:图标位画一叠最多三枚工具图标、名位画摘要句、
  右端画总耗时与失败点)+ **正在跑的那一步**(有的话)。也就是说收起时你永远看得见「现在在干什么」。
- **多步,展开**:头行 + 全部步行,步与步之间一条 `--line-1` 细线,不留 gap;同名连发仍聚成
  「read ×3」一行,点开原位逐条(保留今天的聚合,只换壳)。
- 头行的摘要句由 presenter 的 `name` 拼:前两步的名 + 「+N」,没有「执行了 N 步」这种旁白。
  计数只在「×N」聚合行上出现(那是事实,不是徽)。

### 6.2 三段流中态,每段都看得见「做了多少」

| 段 | 今天 | 本稿 | 数据从哪来 |
| --- | --- | --- | --- |
| **参数生成中** | 工具名 + 半截 JSON + 「参数生成中」 | presenter 加一个 `partial(call)`:对半截 JSON 做**容错前缀解析**(取已闭合的字段),行上画的就是最终那一行的形 —— bash 是命令头词 + 后面逐字长出来的命令、read 是逐字长出来的文件名,尾巴一枚打字光标;右端**不写字**(光标已经说了)。只有认不出的工具才退回原始 JSON | 已经有:`streamingArgs`(`chat-fold.ts:96` 逐 delta 累加) |
| **执行中** | 「执行中」 | 右端画**活的耗时**(`0.4s` 逐帧走,mono,`--text-4`);名位后面那格 summary 画**输出尾行**(bash 的最后一行 stdout、web_search 的「3/5 条」、task 的子步标题);工具报 `ratio` 时卡的底缘画一条 2px 进度条;**允许展开**,抽屉里是正在长的输出(限高,跟尾) | **要新接**:`tool-progress` 活流(6.3) |
| **收场** | 图标定色 + 成果词 + 耗时 | 不变(V2 定稿) | 账本 |

### 6.3 进度流:一条活流,不进账本

```ts
export interface ToolProgressChunk extends StreamChunkBase {
  type: 'tool-progress'
  toolCallId: string
  message?: string      // ToolEvent.progress.message / step.title
  ratio?: number        // 0..1,有就画条
  outputTail?: string   // 最近的输出片段(工具自己截,≤ 2KB)
}
```

产地:工具内核的 `emit(ToolEvent)` 今天已经通到 `ToolRunner` 的观察者(`core/toolkit/events.ts`
`Emit`),只差一段把 `progress / partial / step` 翻成上面这一条并送进 `SessionStreamCoalescer`
(同一根管,16ms 批;合并规则「同一 toolCallId 只留最后一条」)。**不落 `events.jsonl`**:
进度是过程的读数,不是会话的事实,账本里的 `tool/call` + `tool/result` 已经是这次调用的全部真相;
重开会话看到的是结局,与今天一样。这一条要用户拍(拍点 ⑧),因为它是「三定律」旁边的一格例外声明。
第一批产进度的工具:bash(按 100ms 节拍发输出尾)、web_search / web_open(每条结果一发)、
task / agent 类(子步 `step` 事件,`tool-execution.ts:64` 已经有回调位)。read / edit 是瞬时的,不发。

### 6.4 落点

`content/tools/` 三件合成两件:`ToolCard`(卡 + 头行 + 步行)与 `ToolDrawer`(不变);
`ToolPresenter` 加 `partial?(call)`(缺席 = 原始 JSON 尾巴)与 `progress?(chunk)`(把 outputTail
翻成一句 summary;缺席 = 原样画尾行);`status.ts` 的 `EXPANDABLE_STATUSES` 加 `executing`。
`chat-fold.ts` 的活尾巴多一格 `progress: Record<toolCallId, ToolProgress>`,随消息收场清空。
门:`gate:tool-stream`(伪 provider 发一段参数流 + 伪工具发 20 条进度:行上文字逐帧变、耗时在走、
收场后与账本重放逐像素相同)。

### 6.5 流中态稳定性纪律:不许卡、不许闪(09-04 用户看样例首版:「一卡一闪,体感非常不好」)

样例首版的病根就是这条纪律要禁的东西:每 100ms 把整张卡 `innerHTML` 重建一遍,图标的呼吸动画每次
从头开始、每一行都重新挂 —— 看起来就是闪。产品实现照下面五条走,样例已按同一条改法修过:

1. **行不重挂**:一次调用一行,key = `callId`,从第一个参数 delta 到收场是**同一个 DOM 节点**;流中态
   的每一次变化只改文本节点与 `data-*` 属性(名、摘要、耗时、色调),不换元素。零重挂断言
   (前后是同一个节点)进 `gate:tool-stream`。
2. **几何锁定**:行高固定;耗时与计数 `tabular-nums` 且按最宽读数预留宽度(`00.0s`),数字走动不推邻居;
   摘要单行截断不换行;抽屉长高走 `grid-template-rows` 过渡,进度条走 `width` 过渡 —— 屏幕上没有
   任何一格因为一条 delta 而跳。
3. **节拍**:数据按 16ms 批到达;绘制按 rAF 合并,一帧最多一次;耗时读数 10Hz,只改那一个文本节点;
   同一 toolCallId 的进度「只留最后一条」在 coalescer 里就合掉。
4. **换挡只有三处**(参数收齐 / 开始执行 / 收场)允许改结构,换挡用颜色过渡(`--dur`),不闪不跳;
   呼吸动画只作用于图标的 opacity,不参与布局,不在中途被重启。
5. **门**:`gate:tool-stream` 除零重挂断言外加长帧读数(>16ms 计数)与录屏抽帧 diff(闪烁类报障的
   标准手法,08-28 判例:手感类报障禁纸上诊断)。

样例二版用户仍报「很不流畅」,逐条量出来是另外四种抖,补成第 6–9 条(都是「形不变、只换内容」这一句
的具体化):

6. **收起态的活槽位常驻**:多步卡收起时头行下面永远有一行 —— 正在跑的那一步,没有正在跑的就是最近
   收场的那一步。步与步之间卡不许缩回只剩头行再长出来(样例首版每换一步卡高抖一次)。下一步开始时
   是**这一行换内容**(patch),不是一行卸载一行挂载。
7. **快步骤不闪**:开始后 `MIN_BUSY_MS = 250` 内就收场的步(read / 瞬时工具都是),不经过 busy 形,
   直接以收场形出现;真的要露出 busy 形的行用 120ms 淡入进场,不突现。
8. **结构变化走过渡**:一行变「头行 + 一行」、开合抽屉、并入聚合行,卡的高度用前后两次量高做过渡
   (FLIP,180ms,动效档 none 直切),不突变。
9. **读数定宽**:耗时、计数按最宽读数预留宽度并右对齐(`min-width: 4.5ch`),「339ms → 1.2s」这类换位
   不推邻格;头行的工具图标叠只在工具种类集合变化时重画。

### 6.6 活性读数:分得清「还在收」和「卡住了」(09-04 用户补的真需求)

用户原话:「我现在的状况就是不知道它是不是卡住了。」今天「执行中」「正在生成」两个词在数据停了之后
一个字都不变,所以分不出来。规则只有一条:**每一处流中态都要说出「上一次收到数据是多久之前」**,
判据是静默时长,不是猜测。

```ts
/** 活尾巴上按对象各记一格:文字流按消息,参数流与执行进度按 toolCallId。 */
interface Liveness { lastDataAt: number }   // performance.now() 的时刻,每收到一条 delta / progress 就写
export const STALL_SOFT_MS = 5_000           // 超过它:换成「已 N 秒没收到数据」,图标转 warn 色、停止呼吸
export const STALL_HARD_MS = 30_000          // 超过它:同一行补一句「可能卡住了」,并把「停止」摆到手边
```

| 位置 | 正常(数据在来) | 静默 > 5s | 静默 > 30s |
| --- | --- | --- | --- |
| 消息尾的生成读数(08-31 定稿那一行) | 正在生成 · 耗时 · tokens | 已 N 秒没有新内容 · 耗时(读数每秒走,tokens 不变) | 加「可能卡住了」;「停止」字钮就在这一行,不另起浮层 |
| 工具步:参数生成中 | 命令逐字长 + 光标 | 光标停闪,summary 换成「参数已 N 秒没有新字符」,图标 warn | 同上 + 「可能卡住了」 |
| 工具步:执行中(会报进度的工具) | 耗时在走 + 输出尾行在换 | summary 换成「已 N 秒没收到数据」,图标 warn | 同上 |
| 工具步:执行中(不报进度的工具,如今天的全部工具) | 耗时在走 | 静默从**步开始**算,同一句「已 N 秒没收到数据」—— 这是实话,不是误报:它确实一个字都没报 | 同上 |

两个阈值是数,住在 `tokens`/`motion.ts` 那一层的常量表里(与 `ESC_STOP` 一族同处),不进设置页
(设置极简)。「卡住了」永远不是壳的判断,壳只会说「多久没收到数据」;真正的收场仍是引擎那一侧的
超时与重试(agent-loop 的 turn 级重试、120s 权限降级),这一行读数是让人**看得见**那段等待。
样例:比稿页工具卡的「模拟卡住」按钮就是这一格的形。

## 10. 状态先行三表(骨架,施工前逐件补全)

**叶檐 `PaneLeaf`**
- 生命周期:挂载(树里出现这片叶)/ 首载(第一个 tab 的内容异步到达)/ **换宿主**(整棵树随区域搬:
  center → edge → float,叶不重挂,只换外框;浮窗宿主时檐与浮窗标题栏合一)/ 卸载(最后一个 tab
  关掉或隐藏,叶被剪)。
- UI 生命状态:单 tab(身份带)/ 多 tab(tab 条 + 溢出)/ 有预览 tab(斜体)/ 有隐藏(⋯ 亮)/
  超量(30 个 tab:tab 收窄到图标 + 首字,溢出进 ⋯ 列表,永不换行)。
- 交互状态:tab 的 rest / hover / active(键盘位)/ selected / dragging(源变半透明,浮影跟指针)/
  drop-target(五区高亮);✕ 随 `ui/IconButton`;分隔杆随 `ui/Splitter`。

**全屏层 `FullLayer`**(**W2 施工后按实现改写**;逐条判词写在 `components/FullLayer.tsx` 头上)
- 生命周期:进入(那片叶的身子整块 `appendChild` 进 `[data-full-slot]` —— **React 一格都没动**,
  所以这不是一次挂载;叶原位留空框;**没有动效**,进出各一次直切)/ 退出(内容搬回原位,
  焦点由这一层显式送回**原叶原 tab**;装着它的那一格若已离开树,`full` 当场清零)。
  **「内容切换(全屏里 ⌃Tab 换同叶下一个 tab)」W2 不做**:全屏期间那条 tab 条被盖住,
  换 tab 反而会让全屏层空掉 —— 今天的行为是「活动 tab 换人 = 退出全屏」。
- UI 生命状态:檐带**常驻**(不收起,见 §4.3);Dock 藏 / 唤出(`effectiveDockDisplay`);
  内容 loading / error(错误边界仍是内容那一层的)。
- 交互状态:檐带那颗退出钮随 `ui/IconButton`(sm 22px —— 28px 的檐带装不下 `ui/Button` 的 28px);
  Esc 退(这一层自己认,同时也是退层链第一站);⌘⇧↩ 再按一次退出。

**跟随丸 `FollowPill`**
- 生命周期:只在 browsing ∧ unseen ≠ none 时挂载;pinned 即卸;换会话即卸(进场 = pinned)。
- UI 生命状态:`sent` / `reply` 两句文案;动效档 none 时不做入场滑动。
- 交互状态:rest / hover / focus(全局环)/ active;点击后当场卸载(不等滚动动画)。

**工具卡 `ToolCard`**
- 生命周期:第一步到达即挂(参数流的第一个 delta);每多一步只追加一行,不重挂已有的行;
  收场后与账本重放走同一份模型(流中态的进度格清空,行的形不变)。
- UI 生命状态:一步 / 多步收起(头行 + 活步)/ 多步展开;每步四态:参数生成中(光标)/ 执行中
  (活耗时 + 尾行 + 可选进度条)/ 成功(成果词)/ 失败(原因,红图标);超量(research 几十发)仍走
  检索段,不进这张卡。
- 交互状态:头行与步行 rest / hover / focus / expanded;运行中的行可展开(拍点 ⑩);
  抽屉里的活输出限高跟尾,人往上翻就不跟(与聊天区同一个 `FollowController`)。

## 11. 三个 UI 样例(比稿页可交互;每台都能选)

三稿共用 §1–§5 的同一套模型与同一个交互引擎,只在**檐在哪、隐藏的东西收到哪、落区长什么样、
全屏怎么退**四件事上分道:

- **A 标签在檐**:每片叶顶上一条 tab 条(图标 + 名 + 未保存丸 + ✕),浮窗标题栏就是 tab 条;隐藏的
  tab 收在叶檐右端的「⋯」列表;落区是叶上五块半透明矩形;全屏顶上留 28px 檐带常驻。最接近
  VS Code / 浏览器,学习成本最低。
- **B 丸标签 + Dock 收纳**:tab 是一排圆角丸浮在内容顶部(与壳的暖圆语汇同族),隐藏的 tab 像
  macOS 最小化的窗口一样**缩进 Dock 尾部**成小瓦,点一下回来;落区是带圆角的柔光区;全屏檐带
  自动收成把手。最像这台壳既有的形。
- **C 竖排书签**:打开的内容在叶的左缘排成一列竖签(Arc / Edge 的竖 tab),文件名横排可读、不截断;
  「隐藏」是这一列底部的一节;落区在竖列里是插入线、在内容上是四条边带;全屏时整列隐去,左缘留
  4px 把手。文件多时最能读。
- **D 标签在顶栏**(09-04 追加,推荐):中央区的标签条就是窗口顶栏(红绿灯那一栏),聊天区里零檐、
  宽高与今天逐像素相同;多片叶按阅读序分组排在顶栏上;架子与浮窗的叶檐照 A 画;全屏 = 只剩顶栏
  与内容。落到顶栏 = 并入焦点叶。规则全文在 §2.2。

比稿页另有两块不分稿的样例:**聊天跟随**(§5 的状态机可试:贴底发送、上翻后发送、流式期间上翻、
丸回底;09-04 起输入框是悬浮玻璃,正文从底下流过,命令 / @ / 模型抽屉在块内往上长且开着时转不透明,
生成中的丸是三个点)与**工具卡**(§6 的一张卡按时间轴播:参数逐字长出、执行中活耗时与输出尾、收场、
多步收起 / 展开、「模拟卡住」;按 §6.6 只改文本节点不重建)。

## 12. 不做与留账

- 会话级持久隐藏(隐藏的 tab 跨重启)—— `hidden` 随树按 Workspace 落盘,实例状态(草稿)不落盘;
  重启后隐藏的文件 tab 以「未加载」形回来,草稿丢(与今天关掉应用一样)。要不要落草稿另议。
- 浮窗里的分屏比例持久化走既有 `split-prefs`,键 = 叶 id;叶 id 是 uuid,跨 Workspace 不复用。
- 拖拽的可访问性:键盘搬 tab 走右键菜单「移到 ▸」,不做拖拽的键盘替身之外的东西。
- 置顶(hold-top)档、隐藏 tab 的键位、系统全屏联动的真机验证,各记一格,随拍点走。

**W2 留下的账(真全屏)**
- **聊天区进不了全屏**(`ContentKind.fullable: false`):输入框还挂在外壳的 `.center` 上、不在树里。
  W5 把 composer 归给焦点所在的 chat 叶之后删掉那一行。
- **檐带常驻,不自动收起**(拍点 ⑥ 只取了样例 A 那一档;样例 B 的「2s 收成把手」不做)。
- **全屏期间换活动 tab = 退出全屏**:全屏里那条 tab 条被盖住,换 tab 会让全屏层空掉,
  所以「⌃Tab 在全屏里换同叶下一个 tab」这一格没有建。要它就得先给全屏层自己一条 tab 条。
- **召唤一块被全屏盖住的面不会答 `blocked`**:`occluderOf` 只认舞台(全屏不是一种 Placement),
  于是 ⌘⇧K 那一族仍然会把面「露出来」——露在一个看不见的地方。要治得让召唤也问一句拼贴台。
- **全屏不跨重启、不跟工作区走**:瞬态,换空间清零。这是有意的(一台重开的机器该先给你看见全貌)。
