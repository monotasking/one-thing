05 / 从类型到实际执行 / 约 7 分钟

这个 emit，
到底怎么执行？

你已经找到了接口类型，却看不到它怎样连到真正的函数。这节课只补上这一段：页面里的 emit 如何创建，又怎样找到后端的 emit。

依据 2026-09-11 工作区源码。回放中的代码是简化教学版本，省略类型细节、错误处理与权限分支，不发真实请求。

01

先理解：名字也可以放在变量里

const api = {};
const method = "emit";

api[method] = function (payload) {
  return sendRequest(payload);
};

api 是一个对象，可以按名字存东西。method 是变量，里面装着字符串 "emit"。方括号会先读取变量的值，所以这里的 api[method] 就是 api["emit"]，也就是 api.emit。

= function (payload) { ... } 把一个函数存到这个位置。此时只是把函数准备好，还没有执行函数体。以后写 api.emit(数据)，才会调用它；这里的 payload 是接收数据的参数名。

依据：MDN：方括号访问属性。注意 api.method 会查找名字就是“method”的项，不会读取变量 method 的值。

method 的值是 "emit"。api[method] 找到哪一项？

先判断，再继续看真实项目。

02

把“准备好”和“真的调用”分开看

先看前后端各自如何准备，再跟着一条“你好”的消息走。客户端生成方法与后端注册处理函数是各自的准备工作，不意味着它们必须按回放顺序先后启动。

准备 1 · 你最初看到的类型

规定数据格式，还没有执行函数

export type SessionCommandRoutes = {
  emit: {
    input: SessionCommandEmitRequest;
    output: SessionCommandEmitResult;
  }
};

type 定义类型说明；export 让其他文件能引用它。这里说的是“emit 接收哪种请求、返回哪种结果”，没有函数体。类型声明不会自动创建方法，也不会发网络请求。

源码：session-command.ts · L46。TypeScript：类型别名。

准备 2 · 告诉运行中的程序有哪些名字

用普通数据登记接口分组和方法名

const sessionCommandRouter = defineRouter(
  "session-command",
  ["emit"]
);

["emit"] 是一个数组，可以理解为名字列表。defineRouter 根据这些值建立路由说明：分组叫 session-command，其中有方法 emit。后面生成客户端和注册后端都会用这份说明。

和上一步的区别这一步提供运行时要读取的名字；上一步提供开发时检查用的类型。原代码里的 <SessionCommandRoutes> 是给 defineRouter 的类型约束。

源码：session-command.ts · L50。上方示例省略了类型参数。

准备 3 · 客户端生成一个函数

api[method] 变成 api.emit

const api = {};
for (const method of router.methods) {
  api[method] = async (payload) => {
    return invoke({
      domain: router.domain, method, payload
    });
  };
}

for ... of 表示逐个取出列表中的名字；这次取到 "emit"。(payload) => { ... } 是函数的另一种写法，async 表示返回 Promise（异步结果）。这段代码给 api 装上 emit 函数；只有以后调用它，才会进入 invoke 发送请求。

客户端对象从这里来const sessionCommands = client.api(sessionCommandRouter)。client.api 通过 createRouterClient 创建这个对象，后续可复用缓存。

源码：router-client.ts · L43–48 / client.ts · L68–73。示例略去了响应处理。

准备 4 · 后端登记另一个函数

把名字与真正的处理函数对应好

ctx.registerRpcDomain(
  sessionCommandRouter,
  sessionCommandRpcHandlers
);

后端的 sessionCommandRpcHandlers 对象上，已经写好了 async emit(request, context) { ... }。注册操作把分组名、方法名和这个函数记到查找表中。

登记的关系 · 概念示意session-command + emit → 后端 emit 函数
登记时保存函数，收到请求后才调用它。

源码：rpc/index.ts · L197 / registry.ts · L88–107。这里没有把前端函数复制到后端。

执行 1 · 用户发送消息

现在才调用页面上的 emit

sessionCommands.emit({
  sessionId: "s1",
  command: {
    type: "command:send-message",
    content: "你好"
  }
});

对象后的点号取出 emit，后面的括号调用它。整组数据进入生成函数的 payload 参数；那个函数再调用 invoke，把分组名、方法名和数据包在一起。

这里有两层名字method: "emit" 决定调用哪个后端接口；command.type 决定接口收到以后，要处理发送、停止等哪一种会话命令。

源码：chat-port.ts · sessionCommands.emit。s1 与“你好”为虚构数据。

执行 2 · 数据跨过网络边界

传过去的是一包数据

{
  "domain": "session-command",
  "method": "emit",
  "payload": {
    "sessionId": "s1",
    "command": {
      "type": "command:send-message",
      "content": "你好"
    }
  }
}

HTTP 传输层用 JSON.stringify 把对象转成 JSON 文本，以 POST /api/rpc 发送。JSON 是记录数据的文本格式。函数代码没有随这包数据发送；后端会按里面的名字寻找自己的函数。

源码：transport/http.ts · L130–134。RPC 就是用请求让另一端执行指定操作；它不是 JS 特殊语法。

执行 3 · 后端按两个名字查表

从请求找到后端的 emit

const entry = domains.get(request.domain);
const method = request.method;

const data = await entry.handlers[method](
  request.payload,
  context
);

后端先把 JSON 文本读回对象，再运行 dispatchRpc。domains.get(...) 按分组名取出已注册的一组方法；此时 method 是 "emit"，所以 entry.handlers[method](...) 就调用这组方法中的 emit。

这次参数如何对应？网络包里的 payload，成为后端 emit(request, context) 的 request。context 由后端提供，携带当前请求的身份、传输等信息。

源码：server/http.ts · L269–283 / registry.ts · L135–189。上方省略了名字校验、访问检查和任务包装。

执行 4 · 提交命令，再返回结果

后端 emit 把命令交给会话系统

async emit(request, context) {
  return emitToBus(
    request.sessionId,
    request.command,
    context
  );
}

实际方法先做访问检查；普通发送命令进入 emitToBus → emitCoreSessionCommandForIpc → eventBus.emit，再由命令处理表触发 handleSendMessage。提交结果经过 HTTP 返回，客户端取出其中的数据。

到这里，仍不等于 AI 回答已完成返回成功说明命令已交出。AI 处理和页面内容回显继续沿消息生命周期中的事件通道运行。

源码：后端 emit · L191 / ipc-operations.ts · L63 / 引擎命令处理表 · L614。
