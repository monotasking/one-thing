02 / 消息的完整旅程 / 约 8 分钟

按下发送之后，
谁接着做什么？

这节课的目标：用自己的话，向别人讲清一条消息怎样经过模型和工具，最后出现在页面上。先认识这条链路用到的几个 JS、Node.js 概念，再跟随一条消息走完一圈；不用记住所有函数名。

依据 2026-09-10 当前工作区源码。主线选用 React 页面、普通文本会话、应用侧执行工具；示例数据为教学虚构，不发起真实请求。

预备

先认识代码里的六件事

1 · JS、Node.js、React 各管什么？

JavaScript（JS）是语言。Node.js 让 JS 可以在页面之外运行，处理文件、网络和服务端工作。React 是构建界面的库：程序状态变了，它据此更新页面。

2 · 前端、后端是职责划分

前端是你看到的界面；后端负责会话、模型请求和工具执行。在桌面应用中，后端也可以就在你自己的电脑上，“后端”不一定指远处的云服务器。

3 · 函数是“一段可调用的操作”

send(text) 表示现在调用 send，把 text 交给它。send 没有括号时，可以把这个函数交给别人，留待以后调用；这种用途就叫回调。

4 · 对象是“带名字的一组数据”

{ content: "你好", sessionId: "s1" } 把正文和会话编号放在一起。message.content 是取其中的正文；port.sendMessage(...) 则是在调用对象里的一个方法。

5 · Promise 与 await：等结果，再继续

网络请求需要时间。Promise 表示一个尚未完成的结果；await 让当前 async 函数等到结果再往下执行。等待期间，运行环境仍可处理其他任务，不必冻结整个页面。

6 · 事件订阅：先登记，再接通知

on("text", show) 登记“收到 text 就调用 show”。稍后发布方发出 text，接收函数才被调用。因此你只看发送函数的下一行，可能找不到后续处理。

用 5 行教学代码，把这些词连起来
// 简化示意，不是项目原代码
function show(text) { /* 将文字交给界面 */ }
events.on("text", show);           // 先登记回调，没有调用 show
async function send(text) {
  const result = await api.send(text); // 等“命令已交出”的结果
}

const 声明一个变量名；这里用 result 接住结果。async 标记这是一个返回 Promise 的函数。后续 AI 文本从事件通道到达时，登记过的 show 才会执行。发送函数的返回路径与事件回调路径可以分开。

() => ... 是另一种函数写法，常用来写短回调。本项目使用 TypeScript（TS）：在 JS 基础上加入类型标注，帮助开发时检查数据；理解主流程时先关注调用和数据流即可。

基础概念出处：MDN：回调 · MDN：await · Node.js 简介 · React 渲染。还想看事件怎样找到接收函数，可做第 1 课的回放。

01

先记住四个参与者

页面 → 应用后端

页面接收输入和展示结果。后端管理会话、请求模型、执行工具并记录进展。

AI 模型 ↔ 工具

模型生成文本或提出工具调用。工具负责具体操作；MCP 是应用连接外部工具的一种标准接口。

发送消息→请求模型→执行工具（如需要）→携结果再问模型→回答结束

页面回显贯穿整个过程。它从后端订阅进展，陆续显示用户消息、工具状态和正文；不用等模型全部做完。

源码依据：请求与事件的两条通道。概念依据：OpenAI 官方工具调用流程。

02

跟着一条消息走

假设已经接好一个天气 MCP 工具。用户输入：“查一下杭州天气，告诉我出门要不要带伞。”点下一步，观察当前交接的是消息、调用请求，还是结果。

一次发送 · 两次模型请求 · 一次工具执行教学回放

应用后端会话与执行循环
AI 模型生成与选择
工具服务本例走 MCP

① 用户 → 页面

点击发送，先把消息交出去

按钮提前登记了点击回调。点击后，它调用发送函数 doSend；普通文字继续交给 sendPlain 和页面的数据管理函数 chat-source.send。页面先放一个待发送气泡，再异步发请求。首次对话还会先创建会话。

此刻页面先显示“查一下杭州天气……”的待发送气泡，并清空输入框。

源码：Composer → useComposerSend → chat-source.send。已识别的斜杠命令可能在这里另行处理。

② 页面 → 应用后端

发出的是“开始处理这条消息”的命令

页面的发送接口 chatPort.sendMessage 发出 command:send-message。数据通过 HTTP 请求送到后端：POST 是请求方式，/api/rpc 是接收地址的路径。后端校验访问权限，再交给命令总线——按命令名字寻找处理函数的分发器。

返回值的含义success: true 表示命令已成功交出；回答仍可能正在生成，或者稍后发生错误。

源码：chat-port.ts · connection.ts · session-command.ts。桌面壳也使用这套 HTTP 客户端。

③ 后端命令总线 → 会话引擎

准备这一轮对话

提前登记的命令处理函数调用 handleSendMessage。引擎记录用户消息、解析引用、选择模型与凭据，准备历史和系统提示，创建助手消息与执行记录；需要时先压缩上下文。

此刻页面后端记录被事件同步回来；正式用户消息接替待发送气泡，随后进入助手运行状态。

源码：core-stream-engine.ts。若同一会话已在运行，普通文字会进入 steering 队列，交给当前执行处理。

④ 应用后端 → AI 模型 · 第一次请求

模型收到的不只有最新一句话

请求包含系统提示、会话历史、用户消息，以及本次可用工具的名称、说明和参数结构。Provider 适配器把这些内容转换成所选服务的请求格式，并读取流式响应。

模型看到的工具说明 · 简化示意get_weather(location: string)：查询指定城市的天气。模型拿到的是调用说明，执行代码仍在工具端。

源码：stream-runtime.ts → runAgentLoop → HttpAgentProvider。本例工具名省略了项目里的命名映射。

⑤ AI 模型 → 应用后端

模型提出“请调用这个工具”

模型返回一个结构化工具调用：工具名、参数，以及用于关联结果的调用 ID。循环找到对应工具，解析和校验参数，再经工具执行器检查权限、执行操作。

本例调用 · 简化示意{ id: "call_1", name: "get_weather", args: { location: "杭州" } }

源码：executeAgentToolCall → executeToolDirectly → ToolRunner。若需要用户审批，执行会等待审批结果。

⑥ 应用后端 → MCP 工具服务

MCP 把调用送到外部服务

本例的工具来自 MCP，执行路径进入 McpTool.apply，经过 Bridge 和 Manager，交给 MCP Client。Client 向对应 Server 发送 tools/call；服务端执行天气查询。

此刻页面工具步骤可以显示“正在调用”。内置工具也走统一执行器，但由自身实现直接执行，不经过这段 MCP 连接。

依据：项目 MCP 链路 · MCP tools/call 规范。

⑦ MCP 工具服务 → 应用后端

工具结果有两个去向

天气工具返回“杭州，小雨”。后端一边更新工具的执行状态和结果，让页面展示；一边把结果按调用 ID 对应好，加入下一次模型请求的上下文。

此刻页面工具步骤显示查询结果。但“是否带伞”的自然语言回答可能还没生成。

源码：runner.ts 中的 tool-result、role: 'tool' 与 messages.push。工具失败也可以作为错误结果交回模型。

⑧ 应用后端 → AI 模型 · 第二次请求

把刚查到的事实交给模型

循环带上此前对话、模型自己的工具调用和对应结果，再请求模型。本例中模型据“小雨”回答“建议带伞”。如果它还需要另一个工具，循环会继续。

抓住这个区别用户只点了一次发送；为了完成这次任务，应用可以请求模型多次。

源码：runAgentLoop 的循环与继续条件。无工具调用、无其他继续条件时，正常结束。

⑨ AI 模型 → 后端 → 页面

增量经过处理，变成可显示的消息

“流式”是结果分多次到达；每次新增的一小段叫“增量”。后端解析并推送它们。页面通过 SSE——一条持续接收服务器通知的 HTTP 连接——收到事件回调，合成新的消息状态，再由 React 把状态画到页面上。

此刻页面 · 增量示意“杭州” → “杭州有小雨” → “杭州有小雨，建议带伞。”

源码：chat-source（管理数据）→ materializeChatMessagesCached（组装消息）→ ChatStream（渲染消息）。这一通道在前面各步也持续工作；此处单独放大说明。

⑩ 应用后端 → 页面 · 收尾

结束的是这一轮执行

后端完成内容与用量等收尾，记录执行结束。页面依据结束状态撤下运行标记。重新打开会话时，页面先订阅新事件，再拉历史记录重建消息。

此刻页面回答保留，运行状态结束。停止或错误也各有对应的收尾路径。

源码：会话事件记录、chat-source.load / onEvent / compose。刷新恢复与实时逐字显示使用的资料有所不同。

共 10 步

这是按职责展开的教学顺序，不是性能时间线。实际执行可以交错：文字先到先展示，完整工具调用一到就可进入调度；不会等整轮回答结束才显示进展。

先试着说出：谁发送、谁请求模型、谁执行工具、结果去哪、页面怎么更新。再展开对照。

展开一段参考讲法

“点击发送后，页面把消息命令交给应用后端。后端准备历史、提示和可用工具，去请求模型。模型可以直接回答，也可以提出工具调用；应用负责执行，外部工具可以通过 MCP 连接。工具结果既更新页面，也回到模型上下文，所以一次发送可能包含多次模型请求。整个过程中，后端持续推送事件，页面把记录和增量合成消息并显示，最后随执行结束收尾。”
