Reference / 2026-09-10 源码快照

一条消息，三种交接。

页面向后端交消息；后端与模型交换上下文和回答；后端与工具交换调用和结果。页面还持续接收后端的状态事件与增量。

一眼看全程

页面 ── POST /api/rpc：发送命令 ──→ 后端会话引擎
                                      │
                        历史 + 提示 + 工具说明
                                      ↓
                                   AI 模型
                                      │
                          文本 / 结构化工具调用
                                      ↓
后端 Agent Loop ──→ 工具执行器 ──┬─→ 内置工具实现
       ↑                        └─→ MCP Client → MCP Server
       └──── 工具结果加入上下文 ←───────────┘
       │
       └─ 再请求模型，直到无需继续或触发终止条件

全过程：后端事件 / 增量 ── SSE ──→ 页面状态 ──→ React 渲染

这是普通文本会话、应用侧工具执行的主线。连接可交错进行；MCP 不是每次请求模型都必经的一站。

统一用这几个词

术语在这条链路里的含义
JavaScript / TypeScriptJS 是编程语言；TS 在 JS 基础上加入类型检查。常见的 .ts、.tsx 文件是 TypeScript 源文件。
Node.js在页面之外运行 JS 的运行环境，用于后端网络、文件和服务等工作。它本身不是语言或 AI 模型。
React / 组件React 是界面库；组件是负责某块界面的代码，如 ChatStream。组件读取状态，生成应显示的内容。
函数 / 调用函数是一段可复用操作。send(text) 是调用并传入 text；单独的 send 可以作为值传递。
回调 / callback把函数交给另一段代码，由它在合适时机调用。按钮点击、收到网络事件都会用到回调；回调本身不保证异步。
对象 / 方法对象组织具名数据；对象上的函数称为方法。message.content 读取数据，port.sendMessage(...) 调用方法。
Promise / async / awaitPromise 表示异步结果；async 函数返回 Promise；await 暂停当前 async 函数的后续执行，待结果可用后继续。它不意味着冻结整个应用，也不让 CPU 密集任务自动并行。
订阅 / 发布先把“事件名 → 接收函数”登记好，再在事件发生时调用接收函数。是否同步执行、能否重放旧事件，需要看具体实现。
会话 / session持续保存的一段对话。sessionId 用来把消息和事件送到正确会话。
一次执行 / run引擎登记和收尾的一次运行。可能包含多次模型交互；特殊边界可轮换执行记录。
模型轮次 / turnAgent Loop 的一次迭代，包含模型交互及其工具处理。失败重试可能增加实际 HTTP 请求次数。
Provider模型服务的适配器，负责把统一请求和流式结果转换成具体厂商的格式。
工具定义 / definition名称、说明、参数结构等信息。它让模型知道有哪些能力可用。
工具调用 / tool call某次具体调用的名称、参数、ID。应用据此找到并执行工具。
工具结果 / tool result执行得到的内容或错误，按 toolCallId 与原调用关联，再进入模型上下文。
MCP应用与外部能力服务之间的协议。Client 在应用一侧，Server 提供工具；工具发现用 tools/list，调用用 tools/call。
RPC调用后端方法的请求方式。这里发送命令使用 HTTP POST /api/rpc。
SSE后端持续向页面推送事件的 HTTP 通道。这里入口是 GET /api/events。
增量 / delta新到的一小段正文、推理内容或工具参数。一次增量不保证等于一个汉字或一个 token。
账本与投影账本记会话事实；投影把记录按顺序归并成当前状态，再组装成界面可用的消息。

术语依据：下方项目源码；MCP 的发现与调用参见官方 Tools 规范（固定版本）。

源码地图：按执行顺序回查

链接打开原文件；行号供编辑器定位，后续代码变化时优先按函数名查找。标注为“主线”的步骤省略了适配类型和旁路。

1. 发送按钮 → 页面发送状态
  • Composer.tsx · L170 / L518：useComposerSend 得到 doSend；按钮空闲时发送，忙时执行停止。
  • useComposerSend.ts · L161 / L203：sendPlain 与命令分流；没有会话则惰性创建。回车和点击共用这条入口。
  • chat-source.ts · L1455：send 增加 pending overlay、递增 sentTick，异步执行 dispatch（L1377）。
2. 两条网络通道：发命令、收进展
  • chat-port.ts · L152：sendMessage → sessionCommands.emit，命令为 command:send-message，文件标记在这里展开。
  • connection.ts · L117 / L136：桌面从 onethingHost.getConnection() 取得连接信息，Web 使用同源地址；都创建 createHttpTransport。
  • http.ts · L130 / L195：调用走 POST /api/rpc；事件走 GET /api/events?after=…。它们不是“发送接口返回完整 AI 回答”的关系。
  • session-command.ts · L178 / L190：sessionCommandRpcHandlers.emit → emitToBus → emitCoreSessionCommandForIpc。后端先检查会话访问权限。
  • core-stream-engine.ts · L610：命令处理表把 SEND_MESSAGE 对应到 handleSendMessage，并不等待整轮回答完成才结束命令处理。
  • 阅读提示：名称里有 IPC_CHANNELS 不代表这个 React 壳此处实际走 Electron IPC。判断传输要看 connection.ts 的具体装配。
3. 会话引擎 → 执行模型循环
  • 产品 StreamEngine · L145：覆写 handleSendMessage，加入产品层的路由与身份处理，再进入 core 的模板步骤。
  • CoreStreamEngine · L887：performSendMessage 准备会话，创建用户消息（L949）、选择 Provider（L992）、创建助手消息和 run（L1014），最终 executeMessageStream（L1062）。
  • stream-executor.ts：宿主流执行入口；普通文本主线进入 executeAgentLoopStreamGeneration，特殊输出有分支。
  • agent-loop-executor.ts：装配生命周期、消费统一流式事件、记录和推送结果。
  • 第一条消息的自动标题生成是旁路，不应把标题请求误算为主回答的第一轮。忙时文字进入 steering 队列；persistOnly 则只记录消息。
4. 历史、提示、工具定义 → Provider → 模型
  • 装配层 agent-loop-runtime.ts · L135：buildAgentLoopRuntimeFromStreamContext 提供提示构建、模型选择、工具执行等宿主能力。
  • 产品 stream-runtime.ts · L818 / L872 / L987：解析本次可见工具、构建请求上下文，再 buildAgentLoopRuntime。
  • toolkit/host.ts · L45 / L69：resolveToolkitSurface 根据会话场景、允许列表与设置选择工具；toolkitAgentSourceTools 提取定义。
  • runner.ts · L571 / L623：循环中把 model / messages / tools / abortSignal 等交给 executeProviderTurn。
  • http-agent-provider.ts · L105 / L145 / L154：buildBody → send → parseStream。这是 HTTP Provider 的共同流程；具体请求格式由协议适配器决定。
  • openai-chat-wire.ts：一个具体协议示例。不能把它的字段格式推广到所有 Provider。
5. 结构化工具调用 → 校验与执行
  • runner.ts · L310：executeAgentToolCall 按名字找到工具、解析参数，并提供 sessionId、messageId、toolCallId、取消信号和进展回调。
  • tool-execution.ts · L51 / L100：executeToolDirectly → runToolkitToolDirectly。
  • toolkit/wiring.ts · L250 / L333 / L371：从 Catalog 找工具，准备工具实例，装配权限与进展观察器，再 runner.run。
  • ToolRunner · L176–193：validator.parse → tool.plan → authorizer.decide → tool.apply。结果经过输出预算处理，再发出完成事件。
  • 权限允许才会执行；需要审批时可以等待用户响应。当前应用工具审批主要在工具执行链路内部等待，不能把旧的“暂停后另调 resume 接口”当作普通发送必经流程。
6. MCP 工具：发现与调用是两件事
  • 发现与暴露：连接或刷新服务时获取工具定义。mcp-catalog.wiring.ts · L56：syncMcpToolsIntoCatalog 将 MCP 能力包装成 McpTool 注册进统一目录。
  • bridge-runtime.ts · L97：getMCPToolDefinitionsForModel 根据设置与工具数量选择逐项暴露或 router 模式。因此模型不一定一次看到所有外部工具的完整定义。
  • 实际调用：external.ts · L282 / L323：McpTool.apply → bridge.execute。
  • bridge.wiring.ts：executeMCPTool → CoreMCPBridgeRuntime → MCPManager.callTool(serverId, toolName, args)，桥接层处理工具引用与目标服务的对应关系。
  • client-runtime.ts · L218 / L234：同一服务的调用进入队列，再调用连接中的 Client，处理超时与结果。
  • 产品 MCP Client · L101：项目支持 stdio、Streamable HTTP 与 SSE 类型的 MCP 连接。MCP 的连接和 UI 的 SSE 是不同链路。
  • 协议原理：tools/list 提供说明；tools/call 发出具体调用。并不意味着每次用户发送都重新发现全部工具。
7. 工具结果 → 下一轮模型请求
  • runner.ts · L646：onToolCallDone 调度执行，按调用 ID 保存结果并发出 tool-result。
  • L747 / L787：把结果构成 role: 'tool' 的内部消息，再将模型消息和工具结果按顺序加入 messages。
  • L799–868：有本地工具调用则通常继续；无此类调用时检查其他继续条件，否则返回。达到轮次上限、取消、错误、工具要求终止等也可能结束执行。
  • 流式细节：参数增量先累积，收到完整调用事件才执行；调用可在 Provider 流还没完全结束时开始。工具完成和模型流收尾需要协调，不能简化为“每个 token 执行一次工具”。
  • 例外边界：externallyExecuted 标记的外部执行调用由其 Provider/Agent 管理，本地循环不会重复执行。本课的“模型提出、应用执行”专指应用侧工具主线。
8. 后端事件 → 页面状态 → UI
  • session-event-recorder.ts：把统一事件记为会话内容、工具和执行事实；文本增量进入记录与实时处理。
  • server/http.ts · L496：subscribeLiveSessionEvents 订阅后端事件和流，分别写成 session:event、session:stream 的 SSE；流增量有合并发送。
  • chat-port.ts · L148：onSessionEvent / onSessionStream 接上客户端事件中心。
  • chat-source.ts · L1914：注册回调；L1936 / L1940 按 sessionId 分发到该会话的数据源。
  • L1070：onEvent 处理账本通知、权限、终止等；L1180：onStream 处理正文、推理、工具输入等实时增量。账本事件不等于所有会话通知，二者不能混为一类持久记录。
  • L564 / L615：compose 合成消息，schedulePush 按动画帧合并更新；正式消息与待发送 overlay 对齐。materializeChatMessagesCached 按节点缓存，合并投影与实时数据。
  • ChatStream.tsx · L108 / L248：订阅 messages，交给 MessageRow 等组件显示正文和工具步骤。
  • 重开会话：chat-source.runLoad（L1325）先订阅，再拉 listRaw 重建历史，避免加载期间漏掉新增事件。大内容可通过 blob 读取。
  • 版本分支：ui-stream.ts 中 ONETHING_UI_STREAM=events 会增加 assistant/delta 等新事件；默认走 legacy。页面另有 STREAM_R2 分支。共同原理都是“记录 + 实时增量 → 消息状态”，不要把某一种 chunk 名称当成唯一实现。

讲解时最容易混淆的四件事

看到的现象准确说法
发送返回成功命令成功交出；回答是否完成要看后续执行状态。
模型“调用”工具应用侧工具：模型输出调用意图，应用检查并组织执行。
MCP 返回了结果工具步骤可以先展示；模型通常还需消费这个结果形成后续回答。
页面正在逐字显示模型流经后端解析与推送，页面再合并状态。显示更新和模型 token 不必一一对应。
